# Python 语言从入门到精通

## README · 导览

### README_1 这套知识库解决什么

这是一套以"实际能力链路"为主轴的语言精进手册。多数入门材料按语法点排队：变量、列表、函数、类……学完仍写不出一个能交付的东西。本册换了编排轴心——按"一段代码被写出来、被读懂对象模型、被抽象、被并发调度、被测试、被观测、被调优、被交付"的真实链路推进。

地基阶段建立最小可运行单元；内核阶段拆开名称绑定、可变性、容器布局与异常语义；抽象阶段进入函数、闭包、装饰器、生成器与数据建模；工程阶段落到包结构、依赖锁定、标准库与质量门禁；精进阶段处理并发模型、解释器机理、系统边界与生产收口。知识点只是骨架，能复现、能记录、能验收才是血肉。

Python 尤其容易被"看起来很简单"误导：语法读得顺，不代表理解了对象引用、可变默认值、GIL 与导入副作用。因此自板块1 起，每个板块固定配齐三样可执行的东西：照着做就能出结果的操作清单、一套对应该场景的笔记记录方法、一组能当场判定成败的验证动作。读完不算学会，验证通过才算过关。

这套手册的"从入门到精通"不是宣传语：README_8 给出入门、进阶、精通三级刻度与晋级判据，0_1 说明七阶段与三级刻度的对应关系，板块1 用一条起步流程把"空目录 → 第一个文件 → 文件夹安排 → 打包发布"跑成实物。

起步目录的安排见 1_1 的目录决策表，发布产物清单见仓库根 `README.md`；`scripts/bootstrap.sh` 会在目标目录生成 `目录安排.md` 与 `dist/发布清单.md` 作为起步样例。

「4」笔记统一采用"场景卡"结构，六字段如下：

| 字段 | 记什么 | 反例 |
| --- | --- | --- |
| 场景 | 当时在做什么、输入是什么 | 只写"研究了列表" |

| 判定 | 通过 / 不通过 / 待查，附依据 | 空着 |
| 迁移 | 下次哪个场景能复用这条结论 | 空着 |

「5」验证统一三段式：命令 → 预期 → 判定。判定必须能被机器或数值确认，不写"感觉快了"。

### README_4 三十分钟起步

第1步：确认解释器与隔离环境，执行 `python --version` 与 `python -m pip --version`，把两行输出原样贴进第一张场景卡的"观察"字段。
第2步：建一个空目录，创建虚拟环境并激活，写一个只打印一行文本的 `main.py`，跑通 `python main.py`。
第3步：为它补一个最小测试，执行 `python -m pytest -q`，看到通过提示后再翻到板块0。

这三步不是热身，而是后面全部板块的验证底座：任何阶段出问题，都先回到这个最小可运行单元，确认是知识问题还是环境问题。

「2」第2步遇到"环境看起来没变却行为变了"的现象，先回到 0_3 基线表与 0_4 取用口径，再怀疑业务代码；解释器分支与信任基础的变化不会出现在版本库差异里。
「3」第3步每次反查结束都要落一张场景卡，把"我以为的原因"与"实际验证出的原因"并排写进"观察"字段；反例清单比索引本身更值钱。

「1」第1步按包方式启动。`python 脚本.py` 在包布局里会让相对导入失效，硬门槛表已改为 `python -m 包名.模块`；干净重建时还要用已安装形态再验一次，不能只靠 `PYTHONPATH` 碰巧可导入。

「2」第2步类型检查必须有命令。9_5 的命令块必须同时含测试、覆盖率与 `python -m mypy 包目录` 三条，只写"类型检查报告无新增错误"而不给命令，等于没有门禁。

「3」第3步环境差异不改判定口径。实测遇到两类适配，处理办法都只改"怎么把命令跑起来"，不碰通过标准。

部分环境未提供 ensurepip，`python -m venv` 会直接失败。做法是备好环境创建工具，或改用带系统站点包的隔离方式；真正不复用宿主站点包的重建另用独立环境创建工具完成。覆盖率数据文件若落在对 sqlite 写不友好的卷上，会报 disk I/O error。

做法是把覆盖率数据与类型检查缓存换到临时目录，而不是跳过覆盖率这一项。

两条的判定仍看"前缀不同、按锁文件重建、同命令重跑结果一致"，12_5 已补这条边界声明。

命令与通过标准见 12_5 的九项判分表。判分表是对照模板，不是标准答案：每次换环境都要自己重跑、自己填"现场判定"列；把别人的"通过"抄进自己的清单，等于把 12_5 的一票否决架空。

### 0_3 环境基线自检

在动笔写任何业务代码前，先把基线固定下来，后续所有"环境背锅"的争论都能用这张表一秒裁决。

| 检查项 | 命令 | 通过标准 |
| --- | --- | --- |
| 解释器可用 | `python --version` | 输出版本标识，无 command not found |
| 隔离环境生效 | `python -c "import sys; print(sys.prefix)"` | 路径指向虚拟环境目录而非系统目录 |
| 包管理器可用 | `python -m pip --version` | 输出版本标识且归属当前解释器 |
| 依赖清单可导出 | `python -m pip freeze` | 输出可解析的包与版本行 |
| 工具链与信任链自更新 | `python -m pip check`、`python -m pip --version` | 无依赖冲突；按官方当前说明核对支持状态与证书信任包，不沿用旧缓存 |
| 格式化与检查可用 | 在环境中执行一次格式检查命令 | 退出码为 0 或明确列出待修文件 |
| 测试可用 | `python -m pytest -q` | 能收集到至少一个用例并通过 |

把表中各项结果原样粘贴进场景卡的"观察"字段，判定写"基线通过"。这张卡在整个学习周期里只需建一次，但每次换机器、换容器镜像都要重跑一遍。

表中 `pytest` 及后续命令里出现的覆盖率插件、构建工具均需单独安装，不在标准库内；本册只描述其用途与验证口径，不假定预装。若选择标准库自带的 `unittest`，把测试命令换成 `python -m unittest discover -v`，验证口径保持不变。

另有一条容易漏的口径：所有存量虚拟环境都要单独走一遍本表，不能只验当前激活的那一个；解释器分支若已终止支持，应记为迁移待办而非继续加固。

三条取用纪律：

「1」第1步先用权威口径定结论，再用教程与练习补手感；两者冲突时以本地实际输出与官方说明为准，不照抄示例输出。
「2」第2步对社区页面做资料甄别：导航分类、官方文档入口、按主题归档的技术版块属于有效信息；推广、重复发布的无信息帖、与语言主题无关的源码交易和广告属于杂项，不进笔记、不进卡片库。
「3」第3步提问与讨论守住协作底线：不人身攻击、与人为善；先给最小可复现片段与已跑过的验证，再描述差异，对方给的结论在本地复跑一遍才归档。

版本与信任链按四个可复跑动作处理。证书信任包、安装器、基础镜像与存量虚拟环境都可能出现"业务代码没变、TLS 客户端的信任基础变了"的情况，这类信息不写死任何版本号或日期：

「1」第1步核对当前解释器是否仍在官方支持范围内；已终止支持的分支不再接收安全修复，应列为迁移待办，而不是继续在上面加固。
「2」第2步清点本机所有存量虚拟环境，逐个更新包管理器与证书相关依赖；更新走官方给出的可信通道，不复用旧缓存，也不只验当前激活的那一个环境。
「3」第3步重建容器镜像时显式拉取基础镜像并按 digest 核对，再禁用层缓存重建，确认新层里的证书集合已更新；把这一步写进交付清单，不靠"上次构建过"推断。
「4」第4步把每次核对的本地输出贴进场景卡的"观察"字段，判定只写"与官方当前公告一致"或"待迁移"，不抄公告里的版本号与日期。

对应到本册：查证动作落在 2_3 的假设—反例卡，依赖与工具链核对落在 6_3 的决策卡，信任链变更落在 11_3 的边界演练清单，最终在 12_3 统一归档。

| 资料类型 | 只取什么 | 明确不取什么 | 归档到哪 |

#### 信任链变更的四类对象

安全公告类资料最容易抄错的，是把"某个包的版本号"当成结论。可迁移的是下面这张表：证书包、包管理器、基础镜像、存量虚拟环境各自会怎么变、各自怎么验。业务代码一行没改，TLS 客户端的前提也可能已经变了。

| 对象 | 会怎么变 | 可复跑动作 | 判定 |
| --- | --- | --- | --- |
| 证书信任包 | 根或中间证书被移除、信任列表调整 | 在干净环境复跑一次外部请求与门禁 | 与官方当前说明一致 / 待迁移 |
| 包管理器与安装器 | 自身携带的信任配置随更新变化 | 清点所有存量虚拟环境并逐一更新，不复用旧缓存 | 全部环境均已核对 |
| 基础镜像与层缓存 | 旧层里仍是旧的证书集合 | 显式拉取基础镜像并按 digest 核对，再禁用层缓存重建 | 基础镜像 digest 已更新，新层门禁复跑一致 |
| 存量虚拟环境 | 当前激活的那个正常，其余仍是旧配置 | 逐个环境打印前缀并复跑门禁 | 全部环境结果一致 |

#### 存量虚拟环境的清点动作

"清点所有存量虚拟环境并逐一更新"如果只写成一句原则，执行时最容易只更新当前激活的那一个。把它拆成四步，每一步都留可粘贴的输出。

| 步 | 动作 | 该看的输出 | 判定 |
| --- | --- | --- | --- |
| 第1步 | 枚举项目目录、用户级环境目录与容器挂载里所有带环境身份标记的位置 | 每处配置文件的路径 | 清单完整，没有"忘了还有这个环境" |
| 第2步 | 对每个环境用它的解释器分别打印环境身份与解释器路径 | 前缀与基础前缀、可执行文件位置 | 每个条目都能说出它属于哪个项目 |
| 第3步 | 对每个环境分别复跑一次导入校验与门禁，不复用旧缓存 | 导入结果、依赖冲突检查、门禁逐条结果 | 全部通过且结果一致 |
| 第4步 | 把清单、逐条输出与"已核对 / 待迁移"写进场景卡 | 一张带最后复核列的核对表 | 没有只写"环境没问题"的合并结论 |

常见误判是把"当前激活的那个正常"当成"全部正常"：旧环境往往不报错，只是仍带着过时的信任配置。第2步逐个打印身份、第3步逐个复跑，目的正是让沉默的那批环境也留下证据。解释器支持状态与证书链分开判定，前者写"待迁移"，后者写"与官方当前说明一致"，不合并。

## 板块1 · 起步：解释器、虚拟环境与第一个可交付程序

### 1_1 核心机理与关键概念

Python 的起步坑几乎都不在语法，而在"到底用的是哪个解释器"。理解三件事即可展开全部工程实践。

第一，虚拟环境是一份独立的解释器视图：`sys.prefix` 指向虚拟环境目录，第三方包落在它自己的 `site-packages` 里，与系统环境互不污染。

第二，`python -m 模块名` 与 `python 脚本.py` 的导入路径不同，前者以当前目录为包根、按模块名解析，后者以脚本所在目录为首位；混用是"本地能跑、别处报导入错误"的高频来源。

第三，依赖清单描述"需要什么"，锁文件描述"确切装了什么"，二者职责不同，可复现构建靠后者。

启动链路画成一条管道，任何一环错位都会在 `sys.path` 或 `sys.prefix` 上露出痕迹。

```text
  命令输入 -> 定位解释器 -> 激活环境视图 -> 解析 sys.path
                 |              |               |
              which/where   sys.prefix     当前目录 / 站点包 / 标准库
                                     |
                                     v
                         import 解析 -> 执行模块顶层代码 -> 入口调用
```

模块顶层代码在导入时就会执行，这一条决定了后面所有的工程约束：不要把有副作用的启动逻辑写在被导入的模块里，入口用 `if __name__ == "__main__":` 守住。

`activate` 脚本常被误认成"切换了解释器"，其实它主要做的是把虚拟环境的可执行目录放到 `PATH` 前面。真正标记环境身份的是目录下的 `pyvenv.cfg`：解释器靠它决定 `sys.prefix` 指向哪里、去哪找站点包。

所以判断环境是否生效，不看命令行提示符前面有没有括号，看下面这组值。

| 观察项 | 期望 | 不达标的含义 |
| --- | --- | --- |
| `sys.prefix` | 指向虚拟环境目录 | 与 `sys.base_prefix` 相同即未进环境 |
| `sys.base_prefix` | 指向系统解释器 | 两值相等说明用的还是系统解释器 |
| `sys.executable` | 虚拟环境内的解释器路径 | 决定包会被装到哪个解释器下面 |
| `python -m pip --version` 的归属 | 与 `sys.executable` 同一环境 | 两者分家时，装了包却导入不到 |

启动方式决定 `sys.path` 的首位，这正是"同一份代码换个命令就导入失败"的根因：

| 启动方式 | `sys.path` 首位 | 常见后果 |
| --- | --- | --- |
| `python 脚本.py` | 脚本所在目录 | 同目录的模块会遮蔽已安装的同名包 |
| `python -m 包名.模块` | 当前工作目录 | 包上下文成立，相对导入才有效 |
| `python -c` 与交互式 | 当前目录或空串 | 适合做基线自检，不适合跑业务入口 |
| 已安装的控制台入口 | 由入口声明决定 | 最接近生产形态，应作为验收口径 |

几个隔离开关专门用来复现"干净环境"，避免本机配置掩盖问题：

| 开关 | 作用 | 用在什么时候 |
| --- | --- | --- |
| `-I` | 隔离模式，忽略环境变量与用户站点目录 | 排查本机配置污染 |
| `-E` | 忽略解释器相关的环境变量 | 验证路径不是被环境变量改出来的 |
| `-S` | 跳过站点初始化 | 观察纯解释器视图 |
| `-X importtime` | 打印各层导入耗时 | 定位慢导入 |

```text
  判定顺序: sys.executable -> sys.prefix / sys.base_prefix -> sys.path[0]
       |              |                       |
   用的哪个解释器   环境是否真的生效      哪个目录先被搜到
```

把这三步按顺序走一遍，比反复重装环境快得多。1_3 的环境快照卡要求原样贴输出，贴的就是这三组值。

**从空目录到第一个文件：目录安排的决策依据**

起步最容易漏的不是语法，而是"为什么这样放文件夹"。板块1 先用单文件跑通最小可运行单元，板块6 再演进到 `src` 布局；两阶段口径不同，但不是矛盾。

| 路径 | 解决什么 | 放错的后果 |
| --- | --- | --- |
| `pyproject.toml` | 项目声明与构建后端 | 只留宽松版本声明，机器无法复现 |
| `main.py`、`calc.py`（起步） | 单文件最小可运行单元 | 还没跑通就先搭复杂包结构 |
| `src/包名`（板块6 起） | 已安装形态与源树隔离 | 靠脚本目录碰巧可导入，打包后子包消失 |
| `tests/` | 用例与实现分离 | 测试跟着源码一起被发出去 |
| `requirements.lock` | 给机器复现的确切集合 | 只剩一句"我这儿能跑" |
| `scripts/` | 门禁、快照、演练脚本 | 环境步骤不可复跑 |
| `dist/`（不入库） | 分发产物 | 产物混进版本库 |

演进口径一致：起步用 `python main.py` 验证单文件；板块6 起统一按 `python -m 包名.模块` 的已安装形态启动，README_5 硬门槛按后者写。目录从第一天留好，后面只往里填文件。

**第一次打包发布**：板块1 就能做，不必等到板块12。`python -m build --no-isolation --outdir dist` 产出分发压缩包，从压缩包内的元数据读出项目名；把产物与一份发布清单放进 `dist/`，并在版本库里排除该目录。

这一步的意义不是发版给别人，而是让"能跑"升级成"能交付"：接手的人拿到产物就能确认它从哪来、怎么重建。完整发布检查见 12_2，起步版实跑见 `scripts/bootstrap.sh`。

### 1_2 可落地操作清单

第1步：新建空目录，执行 `python -m venv .venv`，激活后打印 `sys.prefix`，确认指向 `.venv`（类 Unix 环境用 `. .venv/bin/activate`，Windows 环境用该环境下的对应激活脚本，以后者实际输出为准）。
第2步：执行 `python -m pip --version` 与 `python -c "import sys; print(sys.executable)"`，确认包管理器与解释器属于同一环境。
第3步：写 `main.py`，只做一次输出；再写 `calc.py` 放一个纯函数，验证 `from calc import ...` 能工作。
第4步：把入口逻辑收进 `main()` 并用 `if __name__ == "__main__":` 保护，验证"被导入时不执行、直接运行时执行"。
第5步：执行 `python -m pip freeze > requirements.txt`，再做一次干净环境安装，比对两次输出。
第6步：补一个最小测试，执行 `python -m pytest -q`，看到通过提示后把六条命令存成 `scripts/baseline.sh`。
第7步：按 1_1 的目录决策表核对当前文件落点，把 `dist/` 与虚拟环境目录写进版本库排除清单，并确认 `scripts/` 已存下前面几条命令。
第8步：做一次最小打包发布，用 `python -m build --no-isolation --outdir dist` 产出分发压缩包，从元数据读出项目名，产物与发布清单一起放进 `dist/`。

这八步构成起步流程：从空目录、第一个文件、文件夹安排，一直到第一次打包发布。后续所有板块都在这条链路上叠加能力，而不是另起炉灶。

### 1_3 场景笔记法：环境搭建与首次运行

环境类笔记最容易写成"装好了"，一旦换机器就完全失效。用下面这张"环境快照卡"，关键是保留原始输出而不是结论。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明机器类型、容器镜像标识、虚拟环境目录路径 |
| 预期 | "sys.prefix 指向 .venv；pip 与解释器同源；导入 calc 成功；pytest 通过" |
| 动作 | 逐行粘贴六条命令，不省略参数 |
| 观察 | 原样粘贴 `sys.prefix`、`sys.executable`、`pip freeze` 前几行 |
| 判定 | 四项预期逐条标通过或不通过 |
| 迁移 | "下次新容器先跑这张卡，再写业务代码" |

实用补充：把 `sys.path` 的完整输出贴一次进卡片，之后每次环境异常只比对差异行。笔记里记录的是"差异"，不是重复的成功日志。

### 1_4 案例小故事：两个解释器，一个下午

实习生小周把统计脚本改成小工具，本机跑得好好的，交付时同事一运行就报"找不到依赖"。他反复确认包明明装过，甚至把安装命令又敲了一遍，还是不行。

复盘只问了三个问题：`python` 指向哪个可执行文件？`python -m pip` 用的是不是同一个？激活虚拟环境了吗？三个答案都是"没看"。原来系统里并存两个解释器，包装到了 A，脚本用 B 跑，而两者都有各自独立的站点包目录。

更隐蔽的是，脚本用 `python main.py` 启动，导入路径里混进了同目录一个同名文件，把标准库模块遮蔽了。

修法很朴素：统一用 `python -m pip` 安装、统一用 `python -m 包.入口` 启动、把 `sys.executable` 与 `sys.prefix` 打进启动日志。之后同样的代码在两台机器上输出完全一致。

小周把这张卡贴在笔记首页，标题写的是"能跑不等于在正确的环境里跑"。这条结论一路支撑到板块6 的依赖锁定与板块12 的交付清单。

### 1_5 实用验证：命令、预期与判定

```bash
python -m venv .venv
. .venv/bin/activate   # 类 Unix；Windows 改用该环境 Scripts 目录下的激活脚本
python -c "import sys; print(sys.prefix); print(sys.executable)"
python -m pip --version
python main.py
python -m pytest -q
python -m pip freeze
```

预期：`sys.prefix` 与 `sys.executable` 均落在 `.venv` 内；`pip --version` 归属同一环境；`main.py` 输出那行文本；被导入时入口逻辑不执行；`pytest` 收集到至少一个用例并通过；`pip freeze` 输出可解析的版本行。

判定：把每条命令的退出码接在后面记录，全部为 0 记"通过"。补一条强验证：新建第二个空目录，只按 `requirements.txt` 重建环境再跑一次测试，结果一致才算真正可复现；若结果不一致，先查是否缺了锁定的版本行。

### 1_6 常见误区与进阶钩子

「1」误区：直接敲 `pip install` 而不带 `python -m`。它可能装到另一个解释器下。
「2」误区：把启动逻辑写在模块顶层。用 `if __name__ == "__main__":` 守住，避免导入副作用。
「3」误区：脚本文件与标准库或第三方包同名，造成遮蔽。用 `python -c "import 模块; print(模块.__file__)"` 定位真实来源。
「4」误区：只留 `requirements.txt` 不留确切版本，重建时依赖被悄悄升级。区分清单与锁定两种用途。
「5」进阶钩子：打印 `sys.path` 全部条目并逐条标注它的来源（当前目录、环境变量、站点包、标准库），把标注结果写进场景卡的"迁移"字段。

## 板块2 · 语言内核：对象模型、名称绑定、控制流与异常

### 2_1 核心机理与关键概念

板块1 解决"代码被谁执行"，板块2 解决"一行赋值到底发生了什么"。Python 与许多语言最根本的差别，在于名称不是装值的盒子，而是贴在对象上的标签。

执行 `a = [1, 2]` 是三步：创建对象、把名称 `a` 绑定到它、对象自带类型与身份。再执行 `b = a`，只是又贴了一个标签，并没有复制列表。`is` 比较身份，`==` 比较相等性；`id()` 给出身份标识，只在同一进程内有意义。

可变对象（list、dict、set）原地修改会影响所有绑定到它的名称，不可变对象（int、str、tuple、frozenset）每次"修改"其实新建对象并改绑名称。函数参数传递的也是对象引用，因此"函数里改了列表"会反映到外面，而"函数里给参数重新赋值"不会。

异常是控制流的一部分，不是意外补丁。惯用风格是 EAFP：先做，失败了再按异常类型分流，而不是层层预检。`try/except/else/finally` 四段各有职责：只有成功才进 `else`，无论成败都进 `finally`。

用 `raise ... from err` 保留异常链，用自定义异常类型表达业务语义。

```text
  a = [1, 2]          b = a
   +--------+          +--------+
   |  name a|--------->| list   |<---------| name b |
   +--------+          | [1, 2] |          +--------+
                       +--------+
  a.append(3)  -> 两个名称都看到 [1, 2, 3]
  a = [9]      -> 只把 a 改绑到新对象，b 仍看旧对象
```

表达式层还有几处语法，用对了能明显减少临时变量与嵌套，用错了会悄悄改变求值次数：

| 写法 | 解决什么 | 容易踩的坑 |
| --- | --- | --- |
| f-string | 在字符串里直接嵌入表达式与格式规格 | 格式规格里塞有副作用的调用，难定位求值次数 |
| 赋值表达式 `:=` | 在条件判断里复用一次计算结果 | 为省一行牺牲可读性；循环条件里被重复求值 |
| 结构化模式匹配 `match` | 按数据形状分支，而非逐值比较 | 当成 `switch` 用，忽略捕获模式会绑定名称 |
| 异常组与 `except*` | 一批任务里多个失败一起上报 | 仍用单个 `except`，只拿到第一条 |

`match` 与 `if` 的分界值得单独说清：它匹配的是结构与形状（序列、映射、类及其属性），case 里的裸名称是"捕获并绑定"而不是"比较相等"；要比较常量得用限定名或加守卫。这条判定不弄清，很容易写出"看起来分支齐全、其实每条都命中第一个 case"的代码。

名称查找顺序 LEGB（局部、闭包、全局、内建）在这里同样生效，捕获模式新绑定的名称落在当前局部作用域，可能遮蔽外层变量。

异常组补齐的是批处理场景的缺口：`raise ... from err` 保留一条因果链，而一批任务同时失败时需要把多个异常作为一个组抛出，再由 `except*` 按类型分别处理。它与 `try/except/else/finally` 不冲突，只是把"一条链"扩成"一组链"。

对应到板块8 的并发任务，正好解决"多个子任务失败却只看到第一个"的老问题。

### 2_2 可落地操作清单

第1步：对同一列表分别执行 `append` 与重新赋值，各打印一次 `id()` 与两个名称的值，把差异画成草图。
第2步：用 `is` 与 `==` 各比较一组值，覆盖小整数、长字符串、新建列表三类，记录哪类结果依赖实现细节。
第3步：写一个函数，分别"原地改列表"与"给参数重新赋值"，在调用方打印结果，验证两种改动的传播范围。
第4步：把一段层层 `if` 预检的写法改成 `try/except` 加自定义异常，确认错误分类更清晰。
第5步：用 `raise ... from err` 包装一次底层错误，打印异常链，确认原始原因未丢失。
第6步：用推导式与 `for/else` 各写一遍同一逻辑，体会 `else` 只在未被 break 时执行。

### 2_4 案例小故事：一个默认参数串了三批数据

某批量任务上线后，第三批报表里莫名混进了前两批的记录，且每重启一次就恢复正常、跑一会儿又出现。代码里那个函数签名写着 `def collect(item, bucket=[])`，看起来人畜无害。

默认值对象只在函数定义时创建一次，而不是每次调用新建。于是三次调用共用同一个列表，数据自然越攒越多。把签名改成 `def collect(item, bucket=None)`，函数体里 `if bucket is None: bucket = []`，问题当场消失。

补的测试也极朴素：连续调用两次，断言第二次结果不含第一次的内容。

复盘时大家意识到，这类 bug 之所以难查，是因为它不报错、不崩、单看一次调用完全正确。团队由此定下一条评审口径：函数默认参数出现可变对象，一律打回；同时每条结论进笔记前必须配一张能推翻它的假设—反例卡。这条口径属于评审约定，不靠工具自动检查；板块9 用连续调用的用例把结果钉住。

### 2_5 实用验证：命令、预期与判定

```python
def collect(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

a = collect("first")
b = collect("second")
print(a, b, a is b)
```

```bash
python -m pytest -q
python -m compileall -q .
```

预期：`a` 与 `b` 各自只含自己的元素，二者不是同一对象；把默认参数改回空列表后，第二次调用应看到前一次的元素；`pytest` 全绿；`compileall` 无语法错误。

判定：写一组表驱动测试，覆盖"连续两次调用""显式传入列表""显式传入 None"三类输入，逐类断言内容与身份。三项全绿记"通过"，并额外验证一次"把 `None` 哨兵改回可变默认值后测试变红"——能主动让测试失败，才说明这条断言真的在守东西。

### 2_6 常见误区与进阶钩子

「1」误区：用 `is` 比较值。它只回答"是不是同一个对象"，相等性请用 `==`。
「2」误区：把小整数或短字符串上的 `is` 结果当语言保证。那属于实现细节，不可写进业务逻辑。
「3」误区：`except Exception` 一网打尽，把编程错误也吞掉。按可恢复的异常类型分别处理。
「4」误区：`finally` 里 `return`，会覆盖 `try` 里的返回值与异常。清理逻辑不要改变控制流结果。
「5」进阶钩子：定义一个带 `__eq__` 但不带 `__hash__` 的类，观察它能否放进集合，把报错原文与原因写进假设—反例卡。

## 板块3 · 数据容器与内存视图：列表、字典、集合、切片与拷贝

### 3_1 核心机理与关键概念

板块2 说明"名称贴在对象上"，板块3 说明"一批对象怎么组织"。选容器的本质是在时间复杂度与语义之间做取舍，而不是看哪个写起来短。

列表是动态数组：按下标访问与尾部追加都很便宜，中间插入删除要搬移元素；容量按需扩增，单次扩容成本被后续多次追加摊薄。字典与集合基于哈希表：按键平均常数时间查找，代价是键必须可哈希、内存开销更大、最坏情况会退化。元组不可变，可当字典键，也常用于表达"一组位置固定的字段"。

切片返回新列表（或新元组），但只复制引用，不复制元素对象——这正是浅拷贝与深拷贝的分水岭。

内存侧还有一层：CPython 以引用计数为主、循环垃圾回收为辅。对象每被绑定一次计数加一，解除绑定减一，归零即回收；但互相引用的环需要循环检测器处理。理解这一点，才能解释"为什么闭包或缓存会让对象活得比预期久"。

```text
  original = [[1], [2], [3]]
  shallow = original[:]        deep = copy.deepcopy(original)

  shallow ---> [ ref0, ref1, ref2 ] ---> 同一批子列表
  deep    ---> [ ref0', ref1', ref2' ] ---> 新建的子列表副本

  改 shallow[0][0] -> original[0] 跟着变
  改 deep[0][0]    -> original[0] 不受影响
```

常用操作复杂度速查如下。它回答的是"数据规模涨十倍时，哪一步会先撑不住"，板块10 会拿它做真正的性能判定。

| 容器 / 操作 | 代价量级 | 判定要点 |
| --- | --- | --- |
| 列表按下标取值、尾部追加 | 常数级 | 扩容成本被后续追加摊薄，单次慢不代表整体慢 |
| 列表按值查找、头部插入 | 线性级 | 高频按值查找应换集合或字典 |
| 列表中间插入删除 | 线性级 | 需要搬移后续元素 |
| 字典 / 集合按键存取 | 平均常数级 | 键必须可哈希，最坏情况会退化 |
| `deque` 双端进出 | 常数级 | 单端队列别用列表硬扛 |
| `heapq` 入堆与出堆 | 对数级 | 只取最值时不必整体排序 |
| 全量排序 | 线性对数级 | 只需前几个元素时考虑更窄的选择 |

还有一层容易被忽略的是**视图与副本**。切片会新建容器对象，但元素仍是对原对象的引用；`memoryview` 则连数据都不复制，只是给同一块缓冲区换一个观察窗口。因此处理大块字节时，视图能省下整份拷贝，但也意味着"改视图即改原缓冲区"。

| 写法 | 是否新建容器 | 是否复制元素对象 | 改动是否影响原数据 |
| --- | --- | --- | --- |
| 切片 `s[:]` | 是 | 否 | 改元素内容会，替换某格不会 |
| `copy.copy` | 是 | 否 | 同切片，共享到外层为止 |
| `copy.deepcopy` | 是 | 是（递归） | 否 |
| `memoryview` | 否，是视图 | 否，共享缓冲 | 会，且原缓冲区立刻可见 |
| 推导式 `[x for x in s]` | 是 | 否，元素仍是原引用 | 改元素内容会；只有表达式里显式构造才新建元素 |

把"共享到第几层"写成一句可判定的话，比背容器名词有用：切片共享到元素对象，`deepcopy` 不共享，`memoryview` 连容器都不新建。3_3 的场景卡要求画出动作前后两张草图，画的就是这一列。

### 3_2 可落地操作清单

第1步：对同一嵌套列表分别做切片、`copy.copy`、`copy.deepcopy`，修改第一层子列表元素后打印三者，确认哪一层共享。
第2步：给列表做尾部追加与头部插入各若干次并计时，把量级差异写进笔记，不要求精确数值。
第3步：用不可哈希对象当字典键触发一次报错，再用元组与自定义可哈希对象各成功一次。
第4步：构造一个互相引用的环，用 `gc` 模块观察回收前后的对象数，确认循环垃圾由检测器处理。
第5步：对一份字节数据分别用切片与 `memoryview` 取子区间，比较是否产生整份复制。

### 3_3 场景笔记法：容器选择与拷贝深度记录

容器类问题看不到引用关系就记不住，所以笔记必须以"草图 + 身份标识"为证据。

| 字段 | 本场景填写要求 |

### 3_4 案例小故事：所有分组都拿到了同一个空列表

某报表要按地区把订单分组，开发用一行 `groups = dict.fromkeys(regions, [])` 建好容器，再逐个 `groups[r].append(order)`。跑出来每个地区下面都躺着全部订单，总量翻了地区数那么多倍，却没有一条报错。

原因不在 `append`，而在建容器那一行：`fromkeys` 的第二个参数只求值一次，所有键共享同一个列表对象。它和板块2 里"可变默认参数"是同一族问题，只是藏在标准库 API 的默认值语义里，审起来更像"我明明初始化过了"。改成字典推导让每次迭代新建列表，问题当场消失。

补的测试刻意只建两个键：往第一个键追加一条，断言第二个键仍为空、且两个列表不是同一对象。团队由此把口径从"共享还是复制"细化成"每个键是否各自持有独立对象"，写进 4_3 的契约卡。

12_6 的反模式清单里也多了一条"用共享默认值批量建容器"。这类 bug 不抛异常、不写日志，只把数据悄悄叠在一起。

### 3_5 实用验证：命令、预期与判定

```python
import copy
original = [[1], [2], [3]]
shallow = original[:]
deep = copy.deepcopy(original)
shallow[0][0] = 99
print(original, shallow, deep)
```

```bash
python -m pytest -q
python -c "import gc; print(gc.isenabled())"
```

预期：`original` 与 `shallow` 的第一格都变为 99，`deep` 保持原值；把修改改成外层替换 `shallow[0] = [9]` 时 `original` 不受影响；`gc.isenabled()` 输出为 True 时循环检测器在工作。

判定：把两条修改路径的输出逐条与草图对照，全中记"通过"。再加一道破坏性验证：把嵌套换成不可变元组，重复同样的浅拷贝修改路径，观察是否还能改到内部；能看到这个翻转，说明你真的掌握了"复制的是引用而非元素"。

### 3_6 常见误区与进阶钩子

「1」误区：把切片当深拷贝。嵌套结构必须显式 `deepcopy` 或逐层新建。
「2」误区：用列表做"按值频繁查找"的主结构。换成集合或字典，先用复杂度表判断。
「3」误区：往字典里塞可变对象当键。键必须可哈希且哈希值在生命周期内稳定。
「4」误区：以为引用计数归零就一定立刻释放。含 `__del__` 的环或跨解释器差异会改变时机，以 `gc` 观察为准。
「5」误区：用 `dict.fromkeys(keys, [])` 或乘法 `[[ ]] * n` 批量建容器。第二个操作数只求值一次，所有键或所有行共享同一对象；改用推导式让每次迭代新建。
「6」误区：把 `copy.copy` 当成"只复制一层所以够用"。要写清复制到第几层，并在测试里断言被跳过的那一层是否仍共享。
「7」进阶钩子：用 `sys.getsizeof` 分别量一个列表、一个字典与一个元组在相同元素数下的占用，把数值与"为什么字典更大"写进场景卡。

## 板块4 · 函数与抽象：参数、闭包、装饰器、生成器与类型注解

### 4_1 核心机理与关键概念

板块3 把数据摆平，板块4 决定"行为怎么被复用而不被复制"。Python 的抽象工具很轻，但轻工具最容易用出隐性副作用。

参数分四类：位置、关键字、仅位置、仅关键字；`*args` 收集多余位置参数，`**kwargs` 收集多余关键字参数。默认值在函数定义时求值一次，这个事实在板块2 已用案例说明。

作用域按 LEGB 顺序查找名称（局部、闭包、全局、内建），闭包会捕获外层名称本身而非当时的值，因此循环里创建的一组函数常会"全都记住最后一次的值"——修法是用默认参数或工厂函数把值当场固定。

装饰器本质是"接收函数、返回函数"，`functools.wraps` 用来保留原函数的名称与文档，否则调试与文档生成都会失真。生成器把"一次算完"改成"要一个给一个"，`yield from` 负责委托给子迭代器，内存占用与数据规模脱钩。

类型注解与 `Protocol` 提供静态可读性：注解不强制运行时行为，但配合类型检查工具能把一批错误挡在运行之前。

```text
  调用方 --> 装饰器包装层 --> 原函数
                 |              |
            计时/日志/缓存   只做一件事
                 |              |
                 +-- wraps 保留身份 --+

  列表推导: [f(x) for x in data]   -> 一次性全量在内存
  生成器  : (f(x) for x in data)   -> 迭代时才逐个产出
```

类型注解的价值不在"给变量贴标签"，而在把约束写成可被检查的契约。常用构件分工明确：

| 构件 | 表达的约束 | 典型用途 |
| --- | --- | --- |
| `TypeVar` | 调用时才确定的类型变量 | 输入输出同型的函数 |
| `Generic` | 类或容器对类型变量参数化 | 自定义容器、可替换实现 |
| `Protocol` | 结构化：只要长得像就满足 | 不引入继承的解耦 |
| `Literal` | 取值只能是列举的字面量 | 状态机、模式开关 |
| `TypedDict` | 字典的键集合与各键类型 | 外部 JSON 契约 |
| `Any` 与 `object` | 放弃检查 / 仅保留最宽上界 | 最后手段，不宜作默认 |

`Any` 与 `object` 的区别常被忽略：前者让检查器对该值放行一切操作，等于局部关闭检查；后者是安全的宽上界，只允许所有对象共有的操作。窄化顺序应是"具体类型、联合、`Protocol`、`object`、`Any`"，反过来写等于把类型检查退化成注释。

闭包捕获的是名称所在的单元格，不是当时的值，这也是 `nonlocal` 能改写外层名称的原因：单元格被多个作用域共享，重新绑定发生在单元格上，所有引用它的闭包一起看见新值。

生成器则是另一条双向通道：`yield` 产出值并挂起，调用方可用 `send` 把值送回成为该表达式的结果，用 `throw` 在挂起点注入异常，用 `close` 触发收尾，`yield from` 再把三者透明委托给子迭代器。

因此生成器不只是"省内存的列表"，而是可暂停、可交互的计算单元。

### 4_2 可落地操作清单

第1步：写一个函数同时使用仅位置参数、仅关键字参数与 `**kwargs`，故意传错形式，记录报错原文。
第2步：在循环里创建三个闭包，先观察它们是否都返回同一个值，再用默认参数固定值并复测。
第3步：写一个计时装饰器，分别加与不加 `functools.wraps`，打印被装饰函数的 `__name__` 与文档串。
第4步：把一段"先构造全量列表再遍历"的代码改成生成器管道，对比两份内存占用。
第5步：用 `Protocol` 定义一个只含一个方法的结构化接口，让两个互不继承的类都满足它，跑一次类型检查。
第6步：用 `functools.lru_cache` 给一个纯函数加缓存，验证重复调用命中，并说明为何有副作用的函数不能加。

### 4_3 场景笔记法：函数契约与抽象取舍

抽象层笔记的价值在于"换实现时不翻旧账"，所以用契约卡把隐含约定显性化。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明消费方需要什么能力、当前有哪几个实现或包装层 |
| 预期 | "换实现后调用方零改动；装饰器不丢函数身份；类型检查不报缺失方法" |
| 动作 | 贴出函数签名、装饰器关键行与 `Protocol` 定义 |
| 观察 | 粘贴 `__name__` 输出、类型检查报告首行、内存占用数值 |
| 判定 | 替换成功且身份与类型检查都通过记"通过" |
| 迁移 | "新装饰器先补 wraps；新抽象先问能否用 Protocol 而非基类" |

实用补充：为每个抽象额外记两条"契约外约定"——是否有副作用、是否线程安全。它们不会写进类型系统，却最常在生产里出事，必须落在笔记里。

### 4_4 案例小故事：三个回调全都记住了最后一次

有个批处理界面上放了三个按钮，点击后分别处理三批不同编号的数据。代码用循环一次性创建了三个回调，逻辑看起来干净利落。上线后无论点哪个按钮，处理的都是最后一批编号。

原因是闭包捕获的是外层名称 `batch_id` 本身，而不是创建那一刻的值；循环结束时它早已指向最后一个编号。修法是在创建时把值绑定到回调自己的默认参数里，或者用一个工厂函数当场封住。补的测试也很直接：分别调用三个回调，断言三者结果互不相同。

有意思的是，同一个月里还出了另一件事：有人加了个日志装饰器却漏了 `functools.wraps`，导致监控里所有函数名都变成同一个包装层名字，排障时完全分不清是谁在报错。两件事一起被写进契约卡，标题是"抽象层别把身份弄丢"。

此后评审清单里多了一条：装饰器必须保留原函数身份，闭包必须当场固定值。

### 4_5 实用验证：命令、预期与判定

```python
from functools import wraps

def traced(fn):
    @wraps(fn)
    def inner(*args, **kwargs):
        return fn(*args, **kwargs)
    return inner

@traced
def add(a, b):
    "返回两数之和"
    return a + b

print(add.__name__, add.__doc__)
```

```bash
python -m pytest -q
python -m compileall -q .
```

预期：加上 `wraps` 后 `__name__` 为 `add`、文档串保留；去掉 `wraps` 后两者都变成包装层的信息；三个循环内创建的回调用默认参数固定值后结果互不相同；生成器管道处理大输入时内存占用不随规模线性增长。

判定：做三次主动破坏——删掉 `wraps`、把闭包改回直接捕获循环变量、把生成器改回全量列表，三次都应被测试或可观察数值抓住。全部抓住记"通过"；若某次破坏悄无声息，说明断言或观测有缺口，先补再往下走。

### 4_6 常见误区与进阶钩子

「1」误区：用可变对象作默认参数。改用 `None` 哨兵在函数体内新建。
「2」误区：装饰器不写 `functools.wraps`。调试、文档、某些注册机制都会因此失真。
「3」误区：对有副作用或依赖外部状态的函数加缓存。缓存只适用于输入输出确定的纯函数。
「4」误区：用继承表达"只是长得像"。结构化场景优先 `Protocol`，避免把无关类绑进同一棵继承树。
「5」进阶钩子：写一个既支持迭代又支持 `send` 的生成器，用 `inspect` 查看它的状态，把"挂起—恢复"的观察写成一张假设—反例卡。

## 板块5 · 面向对象与数据建模：类、属性、数据类与协议方法

### 5_1 核心机理与关键概念

板块4 让行为可复用，板块5 让"数据 + 行为"有个稳定的形状。Python 的对象模型并不复杂，但有几处约定一旦搞错，问题会藏得很深。

实例属性查找先查实例字典，再沿类与继承链向上；类属性被所有实例共享，若它是可变对象，一处修改会处处可见——这是板块2 名称绑定在类场景里的翻版。`self` 只是约定名称，代表被绑定的实例。属性访问可以用 `property` 包一层，把校验、懒计算或只读约束收在一处，而调用方写法不变。

数据类适合"主要用来装字段"的模型：它自动生成初始化、 repr、相等性等方法；需要默认值时用 `default_factory` 而不是直接放可变对象；需要不可变语义时用 `frozen=True`。

魔术方法让自定义类型融入语言：实现 `__len__` 与 `__iter__` 就能被 `len()` 与 `for` 使用，实现 `__enter__` 与 `__exit__` 就能用 `with` 管资源，实现 `__eq__` 要注意与 `__hash__` 的一致性。

继承深度宜浅，多继承靠 MRO 与 `super()` 协作；很多场景用组合比继承更好改。

```text
  实例属性查找顺序
  instance.__dict__ -> ClassA.__dict__ -> ClassB.__dict__ -> object
        |                   |
     每个实例独有        全类共享(可变类属性是坑)

  组合优于深层继承
  +----------+  持有  +----------+
  |  Report  | -----> | Exporter |
  +----------+        +----------+
      换导出方式只换被持有者，不动继承树
```

"先查实例字典再沿类向上"只是粗略说法，真正的优先级由描述符协议决定：同时实现 `__get__` 与 `__set__` 或 `__delete__` 的是数据描述符，优先于实例字典；只实现 `__get__` 的是非数据描述符，会被实例字典里的同名键遮蔽。

`property`、`classmethod`、`staticmethod` 以及数据类字段都是描述符的不同外衣。这条规则解释了为什么 `property` 不会被实例属性覆盖，也解释了为什么给实例塞一个同名函数能遮住类上的非数据描述符。

| 查找环节 | 优先级 | 典型代表 |
| --- | --- | --- |
| 数据描述符 | 最高 | `property`、带 setter 的描述符 |
| 实例字典 | 次之 | 普通的 `self.x` |
| 非数据描述符 | 再次 | 实例方法、`staticmethod` |
| 类字典其余项 | 最后 | 类属性、常量 |

`__getattr__` 只在常规查找失败后触发，`__getattribute__` 则在每一次属性访问都触发；后者写错容易递归，通常只应委托给父类实现。

`__slots__` 用固定槽位替代实例字典，能显著降低大量小对象的内存占用，代价是不能随意新增属性、并会影响弱引用与多继承布局，适合先量化再决定。

多继承的方法解析顺序按 C3 线性化：既保持每个基类自身的相对顺序，也保持继承列表里的顺序，两者冲突时在类定义阶段就报错，而不是运行时挑一个。`super()` 不是"调用父类"，而是"沿当前 MRO 的下一个位置继续找"，所以协作式多继承里每个实现都要调用它，链条才不会断。

元类控制的是"类如何被创建"，属于框架层工具；业务模型里出现元类，往往说明该用装饰器、`__init_subclass__` 或数据类来表达了。

### 5_2 可落地操作清单

第1步：定义一个类属性为列表的类，创建两个实例并各自追加，打印两者内容，确认共享。
第2步：把该类属性改成实例属性（在初始化里新建），复测并记录差异。
第3步：用 `@dataclass` 建一个字段模型，覆盖缺省值、`default_factory`、`frozen=True` 三种情况。
第4步：实现 `__len__`、`__iter__` 与 `__repr__`，验证内建函数与打印输出符合预期。
第5步：写一个上下文管理器类，验证无论块内是否抛异常，`__exit__` 都会执行清理。
第6步：把一个三层继承结构改成"一个类持有两个协作者"的组合结构，确认调用方改动最小。

### 5_3 场景笔记法：数据模型与状态变更留痕

建模类笔记要回答"这个对象的状态由谁改、什么时候改"，所以用状态卡记录。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明模型字段、共享状态位置、触发动作是赋值还是原地修改 |
| 预期 | "两个实例状态互不影响；frozen 模型不可改；with 退出必清理" |
| 动作 | 贴出类定义、初始化几行与修改片段 |
| 观察 | 粘贴打印内容、异常类型、清理是否执行的标记 |
| 判定 | 三项都符合预期记"通过"，出现共享污染标出具体字段 |
| 迁移 | "类属性一律先问是否可变；可变就放实例或 default_factory" |

实用补充：给每个模型建一张"字段状态表"，逐字段写明类型、是否可变、缺省语义、是否参与相等性比较。数据类的 `frozen` 与 `eq` 组合最容易在这里踩坑。

### 5_4 案例小故事：所有订单共用了一个"空"列表

某订单模型里写了一句类属性 `items = []`，本意是给每个新订单一个空的明细列表。测试时只创建一个订单，一切正常；联调时创建两笔订单，第二笔里赫然带着第一笔的明细。

排查没花太久：类属性只有一份，两个实例的 `self.items.append(...)` 改的是同一个列表，而"看起来各自为空"只是因为初始化里没显式赋值。

修法是把列表创建移进初始化，改用数据类时则用 `default_factory=list`。补的测试刻意创建两个实例，断言其中一个的明细变化不影响另一个。

复盘时团队顺手清了另外两处同类写法，并把状态卡模板推广到所有模型：字段表里必须标注"可变 / 共享 / 缺省来源"。

后来在另一次改动里，有人给数据类加了 `frozen=True` 却忘了某处仍在原地修改，测试当场变红——这次不再是生产事故，而是一次普通的门禁拦截。这条口径靠用例守住：板块9 的测试创建两个实例，断言彼此不共享可变字段。

### 5_5 实用验证：命令、预期与判定

```python
from dataclasses import dataclass, field

@dataclass
class Order:
    code: str
    items: list = field(default_factory=list)

a = Order("A")
b = Order("B")
a.items.append("book")
print(a.items, b.items, a.items is b.items)
```

```bash
python -m pytest -q
python -m compileall -q .
```

预期：`a.items` 含一项、`b.items` 为空、二者不是同一列表；把 `default_factory` 换成直接给空列表时，数据类应在定义阶段就报错；`frozen=True` 的实例被赋值时应抛出明确异常；上下文管理器在块内抛异常时清理标记仍为真。

判定：逐项对照字段状态表，四项全过记"通过"。加一道破坏性验证：把 `items` 改回类属性形式再跑同一组断言，测试应稳定变红；能看到这个对照，说明"可变类属性共享"确实被验证过。

### 5_6 常见误区与进阶钩子

「1」误区：把可变对象放类属性或数据类默认值。用实例初始化或 `default_factory`。
「2」误区：只实现 `__eq__` 不管 `__hash__`，导致对象不可哈希却毫无提示。按语义成对处理。
「3」误区：继承层次过深、多个父类各改各的状态。优先组合，必要时用 `super()` 明确协作链。
「4」误区：`__exit__` 里吞掉异常却不返回明确结果。清理逻辑要写清楚是否抑制异常。
「5」进阶钩子：打印一个多继承类的 MRO 列表，逐个解释方法解析顺序，再人为制造一次菱形继承，把 `super()` 的调用轨迹写进状态卡。

## 板块6 · 模块与工程化：导入机制、包结构与依赖锁定

### 6_1 核心机理与关键概念

板块5 让单个模块内聚，板块6 让一堆模块能被别人、被另一台机器、被 CI 稳定地重建出来。核心只有一句话：把"我这里能跑"变成"哪里都能跑"。

导入不是文本包含，而是一次带缓存的执行：解释器按 `sys.path` 找模块，找到后执行其顶层代码，把结果放进 `sys.modules`；后续同名导入直接取缓存。由此推出三条工程约束——模块顶层不要有副作用，循环导入往往源于顶层就互相取用，相对导入只在包内有效且依赖"以包方式启动"。

项目布局有一个被广泛验证的收敛形状：`src/` 放包源码，测试放在包外，配置与元数据集中在项目根的一份声明文件里；采用 `src` 布局能逼你以"已安装"的形态测试，而不是靠当前目录碰巧可导入。依赖侧要区分"声明需要什么"与"锁定确切装了什么"：前者给人看，后者给机器复现。

版本号、构建产物元数据与入口声明都写进同一份项目配置，避免散落。

```text
  项目根
  +-- pyproject / 项目配置     声明元数据、依赖、入口
  +-- src/
  |    +-- mypkg/
  |         +-- __init__.py
  |         +-- core.py
  +-- tests/
  +-- 锁文件                   确切版本，供干净环境重建

  导入链路: sys.path -> 找到模块 -> 执行顶层代码 -> sys.modules 缓存
                              |
                         副作用在此发生，所以要克制
```

`sys.path` 只是查找起点，后面还有一套可插拔的查找器与加载器：路径条目逐个交给查找器，命中后由加载器执行模块代码并生成模块对象，`sys.modules` 是这条链的缓存。`importlib` 把这套机制暴露出来，既能按名字动态导入或重新加载，也能按规格构造模块。

插件系统、按配置选择实现、测试里受控替换模块这三类需求都应走它，比手工改 `sys.path` 字符串更可控。

包的形态有两种。常规包由 `__init__.py` 标记，该文件本身就是包的初始化模块，首次导入包时执行，适合放公开的再导出与包级约定，但不宜塞重逻辑。没有该文件的目录仍可形成命名空间包，其路径片段可分散在多个位置并由导入系统合并。

代价是包级初始化代码无处安放。两种形态混用时，最容易出现"本地能导入，打包后某个子包消失"。

| 概念 | 职责 | 误用后果 |
| --- | --- | --- |
| `sys.path` | 提供查找起点 | 靠脚本目录碰巧命中，换启动方式即失效 |
| 查找器与加载器 | 定位并执行模块代码 | 手写路径拼接绕过导入系统，缓存行为不一致 |
| `sys.modules` | 缓存已加载模块 | 测试里直接改它做替换，污染后续用例 |
| `importlib` | 按名字或规格可控地加载 | 用动态执行拼模块名，导入来源无法追踪 |
| `__init__.py` | 常规包的初始化与再导出 | 塞入连接、读配置等副作用 |
| 命名空间包 | 跨位置合并同名包目录 | 误以为包级初始化一定会执行 |

## 板块7 · 标准库实战：路径、编码、时间、日志与子进程

### 7_1 核心机理与关键概念

板块6 把项目立起来，板块7 往里填真实能力。标准库的用法有一个共同倾向：把"自己拼字符串、自己管资源"换成"交给专门对象"。

`pathlib.Path` 用对象表达路径，`/` 运算符拼接、跨平台一致，`read_text` 与 `open` 配合上下文管理器自动收尾。`json` 处理结构化文本，注意数值精度、时间字段需自定义转换、未知字段与编码三项；大文件用逐行或流式思路，别一次读成整份字符串。

`datetime` 最容易出错的是"天真时间"与"带时区时间"混用：比较、算术、序列化都要求两边语义一致，存储统一用带时区表示。`logging` 是分层设施而非打印语句：logger 有层级，handler 决定去向，format 决定字段。

把请求标识放进日志上下文，才能让一条请求在多处日志里串起来。`subprocess` 负责外部命令，参数用列表传递、显式设超时、检查返回码，避免用字符串拼接交给 shell 解释。

```text
  外部世界             标准库边界                 内部代码
  +--------+      +-------------------+      +----------+
  | 文件   | -->  | pathlib / open    |      |          |
  | 文本   | -->  | json / csv        | ---> | 业务对象 |
  | 时钟   | -->  | datetime + tzinfo |      |          |
  | 子进程 | -->  | subprocess.run    |      |          |
  | 运行态 | <--  | logging + 上下文  | <--- |          |
  +--------+      +-------------------+      +----------+
        每一条边界都要写明: 编码 / 超时 / 错误语义
```

还有四处边界，踩中任何一处都不是"写法不优雅"，而是语义直接出错：

| 边界 | 正确做法 | 错误做法的后果 |
| --- | --- | --- |
| 金额与十进制运算 | `decimal.Decimal` 并显式设定上下文精度；从字符串或整数构造，不从 float 构造 | 用二进制浮点累加，或从 float 构造 Decimal，继承尾差 |
| 地区时区 | `zoneinfo.ZoneInfo` 搭配带时区时间 | 手算固定偏移，切换当天的时间戳集体错位 |
| 跨信任边界序列化 | 只用 `json` 等纯数据格式 | 对不可信数据用 `pickle`，反序列化即可执行任意代码 |
| 缓存大对象 | `weakref` 做不延长生命周期的引用 | 全局字典强引用，缓存对象永远不被回收 |

`zoneinfo` 解决的是"偏移不是常量"：同一地区在不同日期可能对应不同 UTC 偏移。存储用 UTC 时刻加 IANA 地区标识，或用 `ZoneInfo` 构造带时区时刻，不要用固定偏移的 `timezone(offset)`；展示时再按地区规则换算。精简容器还需核对 tzdata 是否已安装，否则 `ZoneInfo` 找不到地区规则。

`pickle` 的红线更硬，它反序列化时会按数据里的指示构造对象，只适用于自己完全控制的进程间传递，绝不用于网络输入、用户上传或跨组织的缓存文件。`weakref` 则补上板块3 引用计数那张图的另一半：想"能查到、但不因此留住"时，弱引用是唯一不干扰回收判定的方式。

### 7_4 案例小故事：同一笔订单，两个时区算出了两个日期

某跨境对账报表每天都差几笔，差额不大却从不为零，且只在时区规则切换前后出现。业务代码没做复杂运算，只是把交易时间截成日期再分组汇总。

修法三步：入口统一解析为带时区的时刻，存储保留地区标识；展示换算走 `zoneinfo.ZoneInfo`，不再手算固定偏移；金额一律用 `decimal.Decimal` 并从字符串构造，显式设定精度，避免浮点尾差再叠一层分位误差。

补的测试覆盖切换日前后各一天，断言同一笔交易在两种表示下归属同一日期，且金额合计精确相等。

复盘时把这条写进 7_3 的字段契约表，新增两列"时间是否带时区""金额用哪种数值类型"。此后遇到跨边界数据，先填这两列再写解析代码。这类错误不会抛异常，只会让报表"差一点"。

### 7_5 实用验证：命令、预期与判定

第1步：把下面这段保存为 `verify_subprocess.py`，执行 `python verify_subprocess.py`。用 `sys.executable` 启动慢子进程，避免依赖某个平台自带的 `sleep` 命令。

```python
import subprocess
import sys
from datetime import datetime, timezone
from pathlib import Path

p = Path("data") / "sample.json"
now = datetime.now(timezone.utc)
slow = [sys.executable, "-c", "import time; time.sleep(5)"]
try:
    r = subprocess.run(slow, timeout=0.2, capture_output=True)
    print("未超时，returncode =", r.returncode)
except subprocess.TimeoutExpired:
    print("超时已捕获: timeout ok")
print("路径 =", p, "带时区 =", now.tzinfo is not None)
```

第2步：在完整项目里执行下列门禁命令。

## 板块8 · 并发与并行：GIL 边界、线程、进程与协程

### 8_1 核心机理与关键概念

板块7 让功能跑通，板块8 让功能同时跑起来且跑得明白。Python 并发的第一课不是选库，而是分清任务类型。

在 CPython（标准构建）中，全局解释器锁意味着同一时刻通常只有一个线程在执行字节码；但 I/O 操作与部分 C 扩展会释放锁，所以 I/O 密集任务用线程或协程仍能有效重叠等待，CPU 密集任务则要靠多进程或原生扩展绕开限制。线程适合"等外部"：共享内存方便，代价是必须自己管锁与队列。

进程适合"算得久"：各自独立解释器，代价是数据要能被序列化传递、启动成本更高。`concurrent.futures` 把两者收进同一套提交—取结果的接口，便于切换对比。

协程是单线程内的协作式调度：`await` 处主动让出控制权，事件循环在等待 I/O 时切去跑别的任务；它没有并行计算能力，却能用极小的内存承载大量并发连接。

取消与超时必须显式设计，`Semaphore` 用来做背压，避免把下游一次打满。无论哪种模型，都要先回答"这个任务在什么信号下结束"。

```text
                  任务类型判定
                       |
        +--------------+--------------+
        v                             v
    I/O 密集                      CPU 密集
        |                             |
  threading / asyncio          multiprocessing
        |                             |
  锁 + Queue + 超时         可序列化数据 + 进程池
        |                             |
        +---------------+-------------+
                        v
        concurrent.futures 统一提交接口
                        v
       取消 / 超时 / 背压 / 退出条件表
```

执行器接口看似只有"提交、取结果"两步，但与结果回收相关的接口有四个，选错会让错误被静默吞掉：`Future.result()` 会把子任务里的异常重新抛到调用方，若不取结果，异常就永远留在那个 `Future` 里没人看见。`as_completed` 与 `wait` 只通知完成状态，必须配合 `result()` 才会暴露异常。

| 接口 | 行为 | 适用与风险 |
| --- | --- | --- |
| `Future.result()` | 阻塞取单个结果，异常在此重新抛出 | 不调用即丢弃异常 |
| `as_completed` | 谁先完成就先处理谁 | 适合按完成顺序更新进度；结果顺序不确定 |
| `executor.map` | 按输入顺序返回结果 | 顺序稳定，但最慢一项会拖住整体 |
| `wait` | 按已完成与未完成分组 | 适合超时后单独处理未完成项 |

进程池的数据边界比线程池严格得多：提交的函数与参数必须可序列化，子进程里的修改默认不会回写父进程；要共享状态得走显式进程间通道或托管对象，两者都有额外拷贝成本。因此"把大对象塞进进程池"常是性能回退的来源，更稳的做法是让子进程各自加载、只回传精简结果。

协程侧也有生命周期工具：`TaskGroup` 风格任务组把一批任务当整体管理，任一任务失败时其余被取消、多个异常聚合上报，正好与板块2 的异常组衔接；`wait_for` 管单个任务超时，按完成顺序消费则用对应的迭代接口。

无论用哪种，退出条件表都要写清"谁创建、谁取消、谁等待收敛"，否则任务会挂在无人接收的等待上。

### 8_2 可落地操作清单

第1步：分别用串行、线程池、进程池跑同一段 CPU 密集计算，记录三者耗时，解释为何线程版不明显变快。
第2步：用线程池跑一批带延迟的 I/O 模拟任务，记录耗时，确认等待被重叠。
第3步：用 `queue.Queue` 做生产者—消费者，明确谁发结束哨兵、消费者如何退出。
第4步：写一个协程版批量请求，用 `asyncio.gather` 并发，加 `asyncio.Semaphore` 限制同时在途数量。
第5步：给协程任务设置超时与取消，验证取消后没有遗留任务，打印 `asyncio.all_tasks()` 数量。
第6步：用 `concurrent.futures` 把线程版改成进程版，只换执行器不改业务逻辑，对比调用方改动量。

### 8_3 场景笔记法：并发排障与任务取证

并发 bug 不会稳定复现，笔记必须记录"证据链"而不是"印象"。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明任务数、并发上限、超时时长、执行器类型与输入 |
| 预期 | "取消后遗留任务数为零；结果数与输入数一致；共享状态无竞态；超时可控" |
| 动作 | 贴出执行器创建、取消调用、结束哨兵与等待收敛四处关键代码 |
| 观察 | 粘贴耗时、结果数、`all_tasks()` 数量、异常与取消计数 |
| 判定 | 四项数值同时达标记"通过"，任一不达标写"待查"并保留现场 |
| 迁移 | "凡起任务先写下它的退出条件，写不出就别起" |

实用补充：给每个并发组件建一张"退出条件表"，逐行列出每类任务由谁、在什么信号下结束。评审时只看这张表，能发现八成任务泄漏。

### 8_4 案例小故事：全绿的任务，丢掉的错误

一个批量对账任务每天报"全部完成"，却总有少量记录没落库。线程池提交得很规整，日志里也找不到任何异常。

查到最后发现代码只遍历了 Future 列表统计完成数量，从没调用过 `Future.result()`：子任务里的异常被封存在各自的 Future 对象里，只要不取结果就永不抛出，外层只看到"都跑完了"。

修法两步：每个 Future 都取 `result()`，让异常回到调用方；改用 `as_completed` 按完成顺序处理，把失败项连同原始输入一起记进死信列表，而不是只统计成功数。补的验证很直接——故意让某个子任务抛异常，断言本次批量任务整体判失败、且死信列表里能找到那条输入。

复盘时大家在退出条件表旁边加了一张"结果回收表"：每类任务都要回答"结果由谁取、异常由谁看"。它和取消链路是两件事——任务退出了不等于结果被收走了。这条后来进了 12_6 的反模式清单，也成了板块9 里"假断言"检查的一个真实来源。

### 8_5 实用验证：命令、预期与判定

```python
import asyncio

async def work(i, gate):
    async with gate:
        await asyncio.sleep(0.1)
        return i

async def main():
    gate = asyncio.Semaphore(8)
    try:
        result = await asyncio.wait_for(
            asyncio.gather(*(work(i, gate) for i in range(40))),
            timeout=1.0,
        )
    except asyncio.TimeoutError:
        result = []
    # all_tasks() 含 main 自身，减 1 才是子任务数
    print("收尾后在途任务数(不含 main) =", len(asyncio.all_tasks()) - 1)
    return result

result = asyncio.run(main())
print("结果数 =", len(result), "首尾样例 =", (result[0], result[-1]) if result else None)
```

```bash
python -m pytest -q
python -m compileall -q .
```

预期：程序打印 `收尾后在途任务数(不含 main) = 0`、`结果数 = 40`、`首尾样例 = (0, 39)`；信号量把同时在途数压在设定值 8 附近；把 `timeout` 从 1.0 调到 0.1 后结果数变为 0，超时被捕获且未留下卡住的任务。

CPU 密集任务用进程池明显优于线程池，I/O 模拟任务用线程池明显优于串行。

判定：四项同时满足记"通过"。加一道反向验证：去掉 `wait_for` 只保留 `gather`，并把 `work` 里的等待调到远超观察窗口，此时程序会被拖住、在途任务数不再归零；能看到这个对照，说明取消与超时链路确实生效，而不是碰巧跑完。

### 8_6 常见误区与进阶钩子

「1」误区：拿线程做 CPU 密集计算并期待成倍加速。先分清任务类型，再选执行器。
「2」误区：多进程里传递不可序列化对象或依赖共享可变状态。数据边界要显式设计。
「3」误区：协程里写了阻塞式 I/O，把整个事件循环卡住。改用对应的异步接口或交给执行器。
「4」误区：并发无上限，下游一抖动就被打满。用信号量做背压，并配超时与退避。
「5」进阶钩子：用同一段业务逻辑分别实现线程版、进程版与协程版，把三份耗时与调用方改动量并排写进场景卡，作为板块10 剖析流程的真实负载案例。

## 板块9 · 质量门禁：测试、类型检查、覆盖率与检查流水线

### 9_1 核心机理与关键概念

板块8 让功能跑得稳，板块9 让功能"敢改"。质量不是发布前的一次检查，而是每次改动都自动跑过的一组门禁。

测试框架的核心价值不在断言语法，而在"用例组织能力"：参数化把一组输入压成一张表，fixture 把准备与清理收在一处并声明依赖，`raises` 显式断言异常类型与消息，`monkeypatch` 与 `mock` 把外部依赖替换成可控的假实现，`tmp_path` 提供隔离的文件系统。

类型检查与注解配套，把"属性名写错""传错类型"这类错误挡在运行之前；格式与静态检查统一代码形状，减少评审噪音。覆盖率回答"哪些行被跑到"，不回答"哪些逻辑被证明"，两者不能混为一谈。属性测试更进一步：由工具生成大量边界输入，专抓解析类与算法类代码的意外崩溃。

fixture 的作用域决定它多久重建一次：函数级每次新建，类、模块、会话级在更大范围内复用。作用域越大，越要确认它返回的是不可变对象或每次重建；一旦返回可变容器，用例之间就通过它隐式耦合，表现为"内容没改、换个执行顺序就红"。

因此用例隔离不是靠口头约定，而是靠作用域选择加上"随机顺序再跑一轮"共同验证。

门禁应该分层：格式与静态检查是秒级第一层；单元与集成测试是第二层；类型检查、覆盖率与属性测试是第三层。任何一层变红都不允许合并。

```text
  改动提交
     |
     v
  第1层 格式 / lint / 静态检查      秒级，挡形状与可疑写法
     |
     v
  第2层 pytest 参数化 + mock       挡逻辑回归与边界
     |
     v
  第3层 类型检查 / 覆盖率 / 属性测试 挡类型错、薄弱模块、畸形输入
     |
     v
  覆盖率报告 -> 只看最低的几个模块，不拿百分比当 KPI
```

把"用例组织能力"落到实处，需要三组判据。第一组是 fixture 作用域，它决定状态活多久、清理何时发生：

| 作用域 | 重建频率 | 适合什么 | 风险 |
| --- | --- | --- | --- |
| 函数级 | 每个用例一次 | 默认选择，可变对象都放这里 | 构造成本稍高，但隔离最稳 |
| 类级 | 每个测试类一次 | 一组用例共享只读资源 | 类内用例顺序仍会耦合 |
| 模块级 | 每个文件一次 | 昂贵的只读连接、编译产物 | 跨文件无关，但同文件内会串状态 |
| 会话级 | 整轮运行一次 | 只读配置、一次性启动的服务 | 返回可变容器就等于全局共享 |

```text
  会话开始 -> session fixture 建立
       |
       v
  模块开始 -> module fixture 建立 -> 用例 -> 清理(后进先出)
       |
       v
  每个用例 -> function fixture 建立 -> 断言 -> 清理 -> 还原环境
       |
       v
  会话结束 -> session fixture 清理
  判定: 换随机顺序再跑一轮，结果必须一致
```

第二组是替换的边界。`mock` 与 `monkeypatch` 要打在**对象被查找的位置**，不是它最初定义的位置——`from m import f` 之后，被测模块里已经存了一份本地名称，只替换原模块里的 `f` 不会生效。

另外，`spec` 或 `autospec` 能让假实现保留真实对象的签名，方法名写错时立刻报错；不用它，假实现连不存在的属性都会照样返回一个新对象，测试全绿却什么都没守。每层至少留一条不替换外部依赖的集成用例，否则整套测试验证的只是自己编的剧本。

第三组是检查强度的梯度，从松到紧逐档收紧，不要一上来就全开：

| 档位 | 检查内容 | 何时推进 |
| --- | --- | --- |
| 仅语法与格式 | 形状、未定义名称 | 所有项目立即启用 |
| 基础类型检查 | 显式注解处的类型不一致 | 核心模块注解补齐后 |
| 严格模式 | 未注解函数、隐式 `Any`、缺失返回 | 公共接口稳定后 |
| 禁止隐式 `Any` | 第三方库无存根也要显式声明 | 库代码与对外 API |

断言本身也有机理：测试框架会重写 `assert` 语句，失败时把子表达式的中间值一起打印出来，所以不必自己拼一堆断言辅助函数；`raises` 的 `match` 用于锁定异常消息关键片段，避免"只要抛了任意异常就算过"；浮点比较要用近似断言而不是相等。

属性测试则贵在"收缩"——工具找到一个反例后会自动把它缩小成更短、更简单的输入，因此归档时应保存收缩后的最小反例，而不是最初那一大串随机数据。

### 9_2 可落地操作清单

第1步：把板块2 的收集函数改成参数化用例，覆盖连续调用、显式传容器、显式传 None 三类输入。
第2步：用函数级 fixture 准备一份临时数据文件，断言测试结束后它不污染别处；再换成会话级 fixture 复跑，观察共享状态带来的差异。
第3步：用 `monkeypatch` 把外部调用替换成带 `spec` 约束的假实现，分别模拟正常、超时、畸形响应三种返回；故意打错替换位置，记录"没生效"的现象。
第4步：用 `pytest.raises` 的 `match` 断言自定义异常的类型与关键消息，验证异常链未被吞掉；浮点结果改用近似断言。
第5步：跑一次类型检查与覆盖率报告，找出覆盖率最低的两个模块，各补一条边界用例；把类型检查按梯度收紧一档并记录新增报错。
第6步：为解析函数写一条属性测试，让生成输入覆盖空、超长、特殊字符，把**收缩后**的最小反例固化成普通用例。

### 9_3 场景笔记法：测试用例与失败复盘

测试类笔记的关键不是"通过率"，而是"这条断言在守什么"。用断言意图卡记录。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明被测函数、本次改动、想防住的回归 |
| 预期 | "新增用例在旧代码上变红、在新代码上变绿" |
| 动作 | 贴出参数化用例行与断言行 |
| 观察 | 粘贴测试输出、失败时的期望值与实际值、覆盖率数值 |
| 判定 | 能主动让旧代码失败记"通过"；只是跑绿了记"待查" |
| 迁移 | "每个修复 bug 的提交必须附带一条能复现该 bug 的用例" |

实用补充：建一份"红—绿对照表"，左列写"删掉哪行代码会让哪条用例变红"。复习时按左列抽查，比重新跑一遍全套测试更能发现假断言。卡片再补一栏"是否依赖其他用例留下的状态"，填"是"的先拆依赖，再谈断言强度。

### 9_4 案例小故事：换了个执行顺序，测试就红了

同一套测试在本地按文件顺序跑全绿，CI 换了收集顺序后忽然红一片，且每次失败点都不一样。期间没有任何人改过被测代码。

根因在一个会话级作用域的 fixture：它返回一份可变配置字典，多个用例各自在里面改字段，谁先跑就把状态留给了后面。函数级 fixture 每次新建时完全看不出问题，作用域一放大，用例之间就通过这份共享对象隐式耦合了。

把作用域收回函数级、并让 fixture 每次返回新建字典，顺序怎么换都全绿。

真正改变的是笔记方式：此后每张断言意图卡必须先写一句"这条断言如果失败，说明什么坏情形发生了"，还要额外记一行"本用例是否依赖别的用例留下的状态"。写不出前一句的不许进表，后一句填"是"的先拆依赖。

团队又补了两条门禁：让测试在随机顺序下再跑一轮；把覆盖率报告按模块拆开看，只盯数值最低的那两三个文件。数字不当成绩，只当"哪里还没看过"的索引。这套做法后来延伸到板块10 的性能基线与板块12 的交付清单。

### 9_5 实用验证：命令、预期与判定

```bash
python -m pytest -q
python -m pytest --cov=包名 --cov-report=term-missing -q   # 需覆盖率插件，见 0_3
python -m mypy 包目录                                      # 需类型检查工具，见 0_3；分析目标版本见 pyproject.toml
python -m compileall -q .
python -m pip check
```

命令块里必须同时给出测试、覆盖率、类型检查三条；只写预期不给命令，等于没有门禁。三者各自的判定口径也不同：测试看断言是否变红，覆盖率看未覆盖的具体行号，类型检查看有无新增报错，不能互相顶替。

再补一轮耗时观察与失败即停。顺序扰动由随机顺序插件提供，参数按该插件在当前环境中的说明取，不写死具体开关名：

```bash
python -m pytest -q --durations=5
python -m pytest -q -x
```

预期：参数化用例全部通过；`--cov-report=term-missing` 能列出未覆盖的具体行号；类型检查报告无新增错误；`pip check` 无依赖冲突；模拟超时与畸形响应的用例分别断言到对应的异常或降级结果；属性测试发现的反例已被固化为普通用例。

随机顺序那一轮与固定顺序结果一致；`--durations=5` 能列出最慢的五项。

判定：以"红—绿对照"为准——随机挑三条断言，分别删掉对应实现逻辑后重跑，三条都应变红。全部变红记"通过"；若某条删了实现仍全绿，说明它是假断言，先修断言再继续。属性测试若发现崩溃，把输入固化后重跑直到全绿。

### 9_6 常见误区与进阶钩子

「1」误区：把覆盖率百分比当质量目标。它只说明被执行过，不说明被验证过。
「2」误区：测试里用固定等待去等异步结果。改用事件、队列或带超时的条件等待。
「3」误区：`mock` 把真实行为全替换掉，测的其实是假实现。保留一层不做替换的集成用例。
「4」误区：参数化用例只写合法输入。畸形、边界、并发三类必须各占一行。
「5」误区：把替换打在对象定义处而不是被查找处，或不给假实现加 `spec`。前者替换根本不生效，后者连拼错的方法名都能通过。
「6」误区：会话级 fixture 返回可变字典或列表。作用域越大越要返回不可变对象或每次重建，否则用例靠执行顺序互相传状态。
「7」误区：把属性测试最初那个大随机输入直接归档。应保存收缩后的最小反例，否则复盘时看不出触发条件。
「8」误区：类型检查一上来就全开严格模式，历史代码报错上千条后索性整体关掉。按梯度逐档收紧，每档只清新增报错。
「9」进阶钩子：把一次门禁运行的耗时按用例排序，找出最慢的三个，用 fixture 作用域或假实现优化，把前后耗时写进断言意图卡的"观察"字段。

## 板块10 · 性能与解释器机理：复杂度、剖析、内存与边界

### 10_1 核心机理与关键概念

板块9 保证"改不错"，板块10 保证"改得快且快得有证据"。性能工作最容易走偏的地方，是凭直觉优化一个根本不热的路径。

正确顺序永远是三段式：先测量、再定位、后改动、再测量。测量用 `timeit` 或基准脚本给出耗时与内存基线；定位用 `cProfile` 加 `pstats` 看函数调用次数与累计耗时，用 `tracemalloc` 看内存分配来源；改动只针对定位出的那一处。

解释器侧要理解两件事：引用计数让大多数对象在解绑时即时回收，循环垃圾交给 `gc` 模块处理；对象模型带来的属性字典与装箱成本，使得"选对数据结构"常常比"微调循环写法"收益大得多。板块3 的复杂度表在这里才真正派上用场。

常见有效手段就那么几类：把按值查找换成集合或字典、用生成器替代全量列表、用批量 I/O 替代逐条调用、用缓存复算结果、把热循环里的重复属性查找提出来、必要时把计算密集段交给原生扩展。每一类都必须拿改动前的基线来对照。

```text
  基线测量 -> 剖析定位 -> 单点改动 -> 复测对照 -> 归档数值
     |           |           |           |           |
  timeit     cProfile    只动一处    同样命令    场景卡留存
  tracemalloc  pstats     同输入                 同环境
                 v
       改善不成立 -> 回退改动，保留"此路不通"的笔记
```

再往下一层是字节码与分代回收。`dis` 能把函数反汇编成字节码指令，用来回答"看起来一样的两行代码，为什么多做几次查找"：属性访问、全局名称查找、函数调用在字节码里都是明确指令，热循环里反复做全局查找自然比先绑定到局部变量更贵。

这类优化幅度通常不大，却是看懂剖析结果的基础，也能避免凭语感猜哪行更快。

`gc` 模块管的是引用计数兜不住的部分：对象被分到不同代，新对象更频繁地被检查，活得久的逐步晋升，以此降低扫描成本。由此可推出两条实用判断——互相引用的环会延长存活期，含终结器的对象回收时机更复杂；全局缓存、闭包长引用、注册后未注销的回调，都会让对象比预期活得更久。

观察口径应是"分配速率与存活对象数"，而不是只看某次回收后的总内存。

| 观测工具 | 回答的问题 | 不要拿它回答什么 |
| --- | --- | --- |
| `timeit` | 一小段代码的稳定耗时 | 整条请求链路的瓶颈在哪 |
| `cProfile` 加 `pstats` | 函数调用次数与累计耗时 | 内存分配来自哪一行 |
| `tracemalloc` | 分配位置与峰值 | 对象为何还没被回收 |
| `dis` | 实际生成了哪些字节码指令 | 运行时热点在哪 |
| `gc` 统计 | 各代对象数与回收次数 | 单个对象的确切生命周期 |

测量本身也有口径，读错口径比不测更危险。最常见的是把剖析结果当成绝对耗时：`cProfile` 会给每次函数调用加一层确定性开销，函数多、单次便宜的代码在剖析里显得格外慢，而纯算术循环又显得格外快。

它的用途是排"谁被调得多、谁累计占比高"，不是给最终延迟定值；定值要回到 `timeit` 或端到端基准。

| 口径 | 定义 | 误读后果 |
| --- | --- | --- |
| 墙钟时间 | 含 I/O 等待、调度与锁的真实流逝时间 | 与 CPU 时间混用，把等待当成计算慢 |
| CPU 时间 | 进程实际占用处理器的时间 | 多线程下可能大于墙钟，误判"变慢了" |
| `timeit` 的 number 与 repeat | 每轮执行次数与重复轮数 | 只看单轮，被系统噪声带偏 |
| 取最小值而非平均 | 最快一轮最接近无干扰的真实成本 | 算平均会把偶发调度噪声算进结论 |
| 剖析态耗时 | 插桩后的相对占比 | 当成上线后的绝对延迟 |
| 预热与缓存 | 首次执行含导入、编译与缓存填充 | 把冷启动成本当成热路径成本 |

```text
  端到端墙钟 -> cProfile 定位热点 -> timeit 测单点 -> 复测对照
       |              |                  |              |
    含 I/O 等待    只看相对占比      多轮取最小值    同命令同环境
```

还有一条容易被忽略的纪律：`timeit` 默认会临时关闭垃圾回收，避免回收动作混进计时；因此用基准脚本自测时也要说明是否关闭 GC，否则两次数值不可比。同理，基准函数里必须真正消费计算结果，否则整段逻辑可能被优化掉，得到一条漂亮但为空的基线。

这两条与 9_1 的假断言检查是同一族问题，只是落在解释器侧：看起来全绿，其实什么都没测到。

### 10_2 可落地操作清单

第1步：为热点函数建一张基线表，固定记录输入规模、解释器标识、耗时与内存峰值四项。
第2步：用 `cProfile` 跑一次真实负载，导出统计并按累计耗时排序，找出前三个热点函数。
第3步：用 `tracemalloc` 抓取分配快照，定位分配量最大的代码位置。
第4步：按板块3 的复杂度表检查热路径的数据结构选择，判断是否有"线性查找该换哈希查找"的点。
第5步：只做一处改动（例如把列表查找换成集合），用完全相同的命令与环境复测，算出改善幅度。
第6步：用 `gc` 模块观察一轮回收前后的对象数，记录是否存在存活过久的缓存对象。

### 10_3 场景笔记法：性能基线与改动对照

性能结论必须可复算，所以笔记里"环境条件"与"数值"同等重要。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明负载规模、并发数、解释器与依赖标识、是否关闭其他负载 |
| 预期 | 动手前写"改动后耗时下降且内存峰值不劣化"，不写"应该更快" |
| 动作 | 贴出改动前后的两处代码与完全相同的基准命令 |
| 观察 | 粘贴两轮完整剖析输出与基线数值，保留原始小数位 |
| 判定 | 三轮重复测量趋势一致记"通过"；波动大于改善幅度记"待查" |
| 迁移 | "任何优化提交必须附前后数值；无数值不合并" |

实用补充：单独维护一份"此路不通"清单，记录试过但没改善甚至变差的改动与原因。它比成功清单更值钱，能防止半年后有人把同一个死胡同再走一遍。

### 10_4 案例小故事：核数吃满了，耗时没降

一段纯 Python 的特征统计跑得慢，有人把它拆成八份丢进线程池，监控上机器看着忙了，端到端耗时几乎没变。第一反应是"任务切得不够细"，又加了一倍线程，反而更慢。

按流程跑 `cProfile` 再加一次对照实验才看清：这是纯字节码循环，全局解释器锁让同一时刻只有一个线程在执行，线程池做的只是轮流占用外加切换开销。换成进程池、并把大数组改成"子进程各自加载、只回传精简统计值"之后，耗时才明显下降；而"按线程数继续加码"那套方案被整体回退。

复盘时最被强调的不是那次替换，而是那张基线表：它让"没改善"当场可见。团队由此定下两条规矩——性能改动若拿不出同样命令下的前后数值，评审直接退回；选执行器之前先判定任务属于 I/O 密集还是 CPU 密集，类型判错后面全白做。"此路不通"也要写成卡归档，后来并入板块12 的交付检查单。

### 10_5 实用验证：命令、预期与判定

```bash
python -m timeit -n 100 -r 3 "sum(range(10000))"
python -m cProfile -o profile.out -m mypkg.entry
python -c "import pstats; pstats.Stats('profile.out').sort_stats('cumulative').print_stats(10)"
python -X importtime -c "import mypkg"
python -m pytest -q
```

预期：三轮 `timeit` 数值波动在可接受范围；`pstats` 能明确指出累计耗时最高的函数；`tracemalloc` 快照能对应到具体分配位置；改成集合后耗时下降且内存不劣化；`-X importtime` 输出可读的导入耗时分布；改动后测试仍全绿。

判定：改动前后用同一命令、同一输入规模、同一台机器各跑三轮，取中位数对照。改善方向符合"预期"字段且三轮趋势一致记"通过"。加一道反向验证：把优化改动回退，数值应回到基线附近；回不去说明环境变了或测量有污染，本次结论作废重测。

### 10_6 常见误区与进阶钩子

「1」误区：用一次运行结果下结论。至少三轮取中位数，注意后台负载与缓存预热。
「2」误区：把缓存当万能解药。缓存会延长对象存活期，且对有副作用或输入不稳定的函数有害。
「3」误区：盲目调 `gc` 参数。先看分配来源与存活对象，再决定是否需要干预。
「4」误区：在基准里造一个与真实负载形状完全不同的输入。输入规模与分布必须来自真实场景。
「5」进阶钩子：用 `tracemalloc` 对同一逻辑的列表版与生成器版各抓一份快照，把峰值与分配行数并排写进场景卡，作为"全量 vs 流式"的可复算证据。

## 板块11 · 系统边界：外部 I/O、重试退避、配置与优雅退出

### 11_1 核心机理与关键概念

板块10 把单机内部调顺，板块11 处理程序与"不受自己控制的世界"之间的那圈边界。这圈边界的关键词不是性能，而是不确定性。

外部 I/O 会超时、会半途失败、会返回畸形数据，因此每处边界都要回答四个问题：多久算超时、失败是否重试、重试是否幂等、彻底失败如何降级。重试必须配退避（固定间隔或指数退避加抖动），否则下游抖动会被放大成重试风暴；幂等靠请求标识或业务唯一键保证，否则重试就是重复写入。

板块8 的取消机制在这里成为统一总线：超时与取消要能从入口一路传到最外层调用。

优雅退出是另一半：收到终止信号后，先停止接收新任务，再等在途任务在宽限期内收敛，最后释放连接与句柄。配置与密钥走环境变量或外部文件，真实值不进版本库，样例与真实分离，缺项时程序给出明确报错而不是默默用默认值。健康分为存活与就绪两种，就绪探针要真实反映依赖状态。

可观测性靠结构化日志、指标与请求标识串联——日志里没有请求标识，排障就等于在黑屋里找开关。

证书信任包、安装器与基础镜像属于运行环境的一部分。这类变更不改变业务代码，却会改变 TLS 客户端能否安全连上外部服务，因此要单独列为一次故障注入项；所有存量虚拟环境也要逐个核对，不能只验当前激活的那一个。

```text
  入口 -> 上下文(超时/请求标识) -> 外部调用
                 |                    |
                 |              +-----------+
                 |              | 超时/失败 |
                 |              +-----+-----+
                 |                    v
                 |          退避重试(幂等) -> 降级/返回
                 v
  信号 -> 停止接新 -> 等待在途(宽限期) -> 释放资源 -> 退出
```

四问表之外还有一层更贴 Python 工程现实的判断：**配置从哪来、缺了怎么办**。配置优先级一旦没写清，"本地能跑、线上用了另一套值"就成了常态。

```text
  内置默认值 -> 配置文件 -> 环境变量 -> 显式启动参数
       |            |            |            |
    最低优先     便于本地     容器/CI 常用   最高优先
       |
       +-- 必填项无值时: 启动即报错，不静默用默认
       +-- 样例文件只放占位值，不进真实密钥
```

| 配置项 | 放哪里 | 判定口径 |
| --- | --- | --- |
| 下游地址与超时 | 环境变量或配置文件 | 缺项时明确报错，不拼一个"看起来能用"的地址 |
| 密钥与凭据 | 外部注入，只读 | 样例文件不含真实值，日志里不打印 |
| 特性开关 | 显式参数或环境变量 | 能说明"关掉之后走哪条分支" |
| 地区与时区规则 | 配置 + 标准时区库 | 与板块7 的带时区表示一致，不手算偏移 |

"彻底失败如何降级"也不能只写"返回兜底"，要写清兜底是哪一种，因为不同形态的数据一致性代价完全不同：

| 降级形态 | 用户看到什么 | 适用条件 | 代价 |
| --- | --- | --- | --- |
| 返回空结果 | 空列表并标注"暂不可用" | 只读展示，允许短暂陈旧 | 可能被误当成"确实没有数据" |
| 返回最近一次成功缓存 | 旧数据加时间戳 | 读多写少、允许陈旧 | 要标明数据时刻，否则误导 |
| 返回可解释的错误 | 明确原因与重试建议 | 写操作、涉及一致性 | 用户体验最差，但语义最诚实 |
| 转入排队后续处理 | 已受理、稍后通知 | 可异步完成且能去重 | 需要幂等键与状态可查 |

写操作通常不该"兜底成功"：与其返回一个看似成功的假结果，不如明确失败并让用户决定是否重试。幂等键在这里同时服务两处——重试时避免重复写入，排队后查询状态时能定位同一笔请求。

优雅退出同样要分阶段记录，否则"收到信号就退出"和在途任务被硬掐断之间没有可观测的差别：

| 阶段 | 该做的事 | 记进场景卡的观察 |
| --- | --- | --- |
| 收到信号 | 停止接新，标记不再健康 | 信号类型与接收时刻 |
| 在途收敛 | 等待任务组取消或完成 | 在途数量归零耗时 |
| 资源释放 | 关闭连接、句柄与线程池 | 关闭前后句柄数 |
| 进程退出 | 明确退出码 | 退出码与总关闭耗时 |

### 11_2 可落地操作清单

第1步：给每个外部调用列一张四问表，并把降级形态写成具体一种（空结果、带时间戳的缓存、可解释错误、排队受理），不写"返回兜底"这种模糊项。
第2步：实现带指数退避与抖动的重试，写清初始间隔、乘数、上限与总耗时；只对暂时性失败重试，参数与鉴权错误直接返回。
第3步：为一个写操作加上请求标识，由入口生成、按业务唯一键去重，重复提交返回首次结果；排队场景用同一键可查询状态。
第4步：注册终止信号处理，按"停止接新—在途收敛—释放资源—明确退出码"四阶段记录耗时。
第5步：把存活探针与就绪探针分开；就绪探针真实检查依赖，存活探针只判本进程是否卡死，避免下游抖动触发全体重启。
第6步：把配置改成"默认值—文件—环境变量—显式参数"四级优先，提交一份不含真实值的样例，删除必填项后确认启动即报清晰错误。

### 11_3 场景笔记法：边界故障与降级演练

边界类知识只能靠"故意制造故障"来验证，所以笔记要按故障注入项组织。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明注入的故障类型：延迟、断连、畸形响应、依赖不可用、信任链或基础层变更、终止信号、缺失配置 |
| 预期 | "超时内返回；重试次数不超上限；重复请求结果一致；退出时在途任务收敛" |
| 动作 | 贴出故障注入方式、退避参数、宽限期与探针代码 |
| 观察 | 粘贴耗时、重试次数、返回码、日志里的请求标识链、退出耗时，以及信任链核对的原始输出（证书链验证结果、镜像 digest、逐环境前缀清单） |
| 判定 | 预期四项逐条达标记"通过"，任一不达标保留现场并标"待查" |
| 迁移 | "每新增一个外部依赖，补一行四问表与一个故障注入用例" |

实用补充：建一份"故障演练清单"，把注入过的故障逐条打勾。没被注入过的边界等于没验证过，这条判据在板块12 的总验收里会再出现一次。

### 11_4 案例小故事：业务代码没动，安装全失败了

一次例行重建后，几个服务的依赖安装集体报证书校验失败，而仓库里没有任何代码改动，上一版产物还是好的。排查先排除了下游服务：连的是同一个包索引，故障只出现在部分机器上。

根因在环境不在代码：证书信任链轮换之后，有些机器沿用旧的基础镜像层，有些存量虚拟环境里的包管理器还是旧版本，握手时对不上新的信任基础。更麻烦的是团队只验了"当前激活的那一个环境"，另外几个由定时任务使用的环境一直没被清点。

整改按四个动作落地：核对解释器是否仍在官方支持范围内，已终止支持的分支列迁移待办；逐个清点所有存量虚拟环境并更新工具链与证书相关依赖；重建容器镜像时显式拉取基础镜像并按 digest 核对，再禁用层缓存重建。

把每次核对的本地输出贴进场景卡，判定只写"与官方当前说明一致"或"待迁移"，不抄公告里的具体版本。验证方式是故意用旧层构建一次，确认门禁会拒绝它。

复盘时四问表补了新的一列："信任基础变了，代码要不要改"。答案是通常不用，但验证动作必须重跑。从那以后边界设计不再只讨论"怎么调成功"，也会讨论"代码没动时哪些前提会变"。这份清单后来成了板块12 交付评审的必备附件。

### 11_5 实用验证：命令、预期与判定

```bash
python -m pytest -q
python -m pytest -k "boundary or shutdown" -v
python -m mypkg.entry &
kill -TERM $!
```

预期：慢下游场景下请求在约定超时内返回且重试次数不超过上限；同一请求标识重复提交只产生一条记录；终止信号后服务停止接新、在途任务在宽限期内收敛、进程正常退出；就绪探针在依赖不可用时返回非就绪状态；删除必填配置项后程序给出明确报错；禁用层缓存重建后外部调用可正常建立，门禁测试全绿。

判定：逐项对照四问表与故障演练清单，各项全过记"通过"。加两道破坏性验证：把退避去掉、只保留立即重试，在同样的慢下游下重试次数应显著上升甚至触发限流；用旧的基础镜像层重建一次，信任基础相关的检查应明确拒绝或标记"待迁移"。

两处对照都看得到，才能说明退避与信任链核对确实在起作用，而不是恰好下游恢复了。

### 11_6 常见误区与进阶钩子

「1」误区：重试不加抖动。多个实例同时退避会同步化，形成周期性冲击。
「2」误区：把真实配置或密钥提交进版本库。用环境变量或外部文件，配一份不含真实值的样例。
「3」误区：就绪探针永远返回成功。它必须反映依赖状态，否则流量会被导到还没准备好的实例。
「4」误区：收到终止信号直接退出，不等待在途任务。要设宽限期并按四阶段记录耗时与退出码。
「5」误区：四问表里把降级写成"返回兜底"。要指明是哪一种形态、用户看到什么、数据一致性代价是什么；写操作通常应明确失败而非兜底成功。
「6」误区：配置必填项缺失时静默用默认值，或把真实密钥写进样例文件。启动即报错、样例只放占位值。
「7」误区：把依赖可用性检查塞进存活探针，或对确定性失败也重试。前者会把局部抖动升级成全体重启，后者只是放大无效流量。
「8」误区：幂等键由下游生成或用时间戳拼成。同一业务请求重试两次会拿到两个键，去重与状态查询双双失效。
「9」进阶钩子：给结构化日志加一个采样开关，在高流量下对比全量日志与采样日志的 CPU 开销，把数值写进场景卡，作为板块10 剖析流程的真实负载案例。

## 板块12 · 生产交付、反模式清单与通关总验收

### 12_1 核心机理与关键概念

前面十一个板块各自交付一种能力，板块12 把它们合成一次"能被别人接手"的交付。判断标准不是"我机器上跑通了"，而是"另一个人在干净环境里，按一份清单，能重建、能验证、能回滚"。

一次完整交付包含五层：可复现构建（锁定依赖、固定解释器视图、产出带元数据的分发产物）、配置与密钥（外部注入、样例与真实分离）、可观测性（结构化日志、指标、请求标识）、安全网（门禁全绿、故障演练清单、回滚步骤）、知识归档（所有场景卡可检索、例外有理由）。这五层缺一层，交付就依赖某个人的记忆。

同样重要的是把全册笔记收口。前面各板块留下了不同形态的记录：资料取用卡、环境快照卡、假设—反例卡、引用草图、契约卡、状态卡、依赖决策卡、字段契约表、退出条件表、断言意图卡、性能基线表、故障演练清单。它们不该散在各处，而应汇成一个可按场景检索的卡片库，并配一份索引。

```text
  可复现构建   配置与密钥   可观测性   安全网   知识归档
      |            |           |          |          |
      +------------+-----------+----------+----------+
                           v
                 干净环境按清单重建
                           v
              门禁全绿 + 故障演练通过 + 可回滚
                           v
                     才叫"交付完成"
```

**可回滚性：降级不等于回滚**

交付五层里写了"能回滚"，但不少团队把两件事混成一件：**降级**是依赖坏了仍给一个可解释的响应，**回滚**是把正在运行的代码换回上一版。前者保护单次请求，后者保护整个版本，判据互不通用。

| 维度 | 降级 | 回滚 |
| --- | --- | --- |
| 触发条件 | 下游超时、返回异常、限流 | 新版本上线后门禁或导入校验不达标 |
| 作用范围 | 一次请求或一段时间窗 | 整个已安装版本 |
| 状态要求 | 允许返回带时间戳的旧结果 | 必须能读回新版本已写入的输入 |
| 结束方式 | 依赖恢复后自动收敛 | 显式切换生效目录并复跑门禁 |
| 验收判据 | 响应可解释、不静默给空 | 已安装形态可导入、同一输入输出一致 |

要让回滚真的能演，分发产物先得满足四条判据：

| 判据 | 含义 | 破坏它的做法 |
| --- | --- | --- |
| 版本可辨识 | 分发产物元数据可读出确切版本 | 所有构建都叫同一个名字 |
| 配置外置 | 切换版本不需要改配置内容 | 把版本相关配置写进产物内部 |
| 状态兼容 | 旧版本能读回新版本写过的输入 | 只做向前兼容、不做向后兼容 |
| 切换原子 | 保留上一版安装副本，切换失败可立刻指回 | 就地覆盖站点包，没有可回退副本 |

四条里最常漏的是第三条。只验"包能导入"、不验"新版本处理过的输入在旧版本上结果一致"，等于只演了半程。12_5 因此要求"服务恢复"与"数据无损"同时成立，实战工程的 `scripts/rollback_drill.sh` 把这两项落成可重跑的命令。

### 12_2 可落地操作清单

第1步：整理一份交付清单，逐项写明命令、预期输出、判定人，不写"检查一遍"这种模糊项。
第2步：在干净环境里只凭清单重建虚拟环境、安装锁定依赖并跑门禁；容器构建显式拉取基础镜像并按 digest 核对、再禁用层缓存重建，另清点所有存量虚拟环境的工具链支持状态，把每一步输出贴进交付记录。
第3步：核对配置与密钥：真实值不在版本库，样例可独立启动，缺项时程序给出明确报错。
第4步：跑一遍故障演练清单，逐条打勾，未演练过的边界补一个注入用例。
第5步：跑回滚演练脚本实演一次：从新版本切回上一版安装副本，同时验可导入与同一组输入输出一致。分发产物元数据单独核对，不靠目录名认版本；线上多实例切换另按 0_2 边界声明处理。
第6步：把全册场景卡按"场景类型"归档，建一份索引，确保每张卡的六字段完整、判定不为空。

### 12_4 案例小故事：故障复盘时，找不到那张基线卡

一次线上延迟抖动需要快速判断"能不能先回滚"，值班的人翻遍仓库和聊天记录，只找到一句"上次优化过，快了不少"，没有前后数值、没有当时的负载规模，也没人记得那次改动是否动过数据结构。回滚决策因此拖了很久，最后靠重新压测才敢动手。

问题不在代码，在知识归档。那张性能基线表留在个人笔记里没进卡片库，环境快照卡、依赖决策卡也散在不同地方，索引从来没建过。程序本身一直是好的，但"判断依据"没有跟着程序一起交出去。

补齐的方式不是补文档，而是补"可检索"：全部场景卡按十二类归档，索引里逐类记用途、来源小节与最后复核；环境快照卡、依赖决策卡、性能基线表各自归位，判定为"待查"的卡单独置顶。索引本身进版本库，随每次交付演练一起更新，不再躺在个人笔记里。

验收口径也跟着改了：让一位没参与过开发的人只凭清单和索引，在干净环境重建、跑门禁、调出当时的基线卡对照当前数值，再据此决定回滚。"第三方能不能找到判断依据"成了交付检查单的最后一项。

那次复盘后写在笔记首页的话是：程序跑得起来，只说明它能用；判断依据查得到，才说明它敢改。板块1 里那条"能跑不等于在正确的环境里跑"，到这里补上了另一半。

### 12_5 实用验证：命令、预期与判定

```bash
python -m venv .venv
. .venv/bin/activate   # 类 Unix；Windows 改用该环境 Scripts 目录下的激活脚本
python -m pip install -r requirements.lock
python -m pip check
python -m pytest -q
python -m pytest --cov=mypkg --cov-report=term-missing -q   # 需覆盖率插件，见 0_3
python -m compileall -q .
python -m build   # 需构建工具，见 0_3
```

预期：干净环境按锁定文件安装后 `pip check` 无冲突；测试全绿且覆盖率报告能列出薄弱行；`compileall` 无语法错误；构建产物元数据与项目声明一致；故障演练清单逐项打勾；回滚演练后服务恢复且数据无损；抽查五张场景卡均能复现原结论。

判定：这是全册唯一一次"全项验收"，采用一票否决——上列任何一项不达标，整体记"未通过"，回到对应板块补完再重跑。全部达标后，在索引里把本次验收的命令、输出摘要与判定写成最后一张卡，命名"通关记录"。此后每次重大改动，只需重跑这份清单，不必重读全册。

"全项"必须落到能逐行打勾的载体上，否则一票否决只是句口号。下表随交付清单一并打印，"现场判定"列由执行人手写"通过 / 不通过 / 待查"，不预填、不事后补。

| 验收项 | 命令或动作 | 通过标准 | 现场判定 | 不达标回到 |
| --- | --- | --- | --- | --- |
| 隔离环境 | 新建虚拟环境并打印解释器前缀 | 前缀指向新环境而非系统目录 | 待填 | 0_3 |
| 锁定安装与依赖冲突 | 按锁文件安装后执行 `python -m pip check` | 无冲突，清单可逐行解释 | 待填 | 6_5 |
| 语法与导入 | `python -m compileall -q .` 并以包方式启动入口 | 无语法错误，不靠脚本目录碰巧可导入 | 待填 | 6_1 |
| 测试与随机顺序 | 门禁脚本加一轮顺序扰动 | 两种顺序结果一致，无状态耦合 | 待填 | 9_5 |
| 覆盖率薄弱行 | 生成含未覆盖行号的报告 | 能定位到具体行，最低的两个模块各有边界用例 | 待填 | 9_3 |
| 产物元数据 | 干净环境构建并读取分发产物元数据 | 与项目声明一致 | 待填 | 6_5 |
| 信任链与基础层 | 禁用层缓存重建并复跑门禁 | 与官方当前说明一致，旧层被明确拒绝 | 待填 | 11_3 |
| 故障演练与回滚 | 跑 `scripts/rollback_drill.sh`：两份副本切换、逐行比对、旧版本复跑门禁 | 注入项全覆盖；可导入与输入一致，输出演练通过标记 | 待填 | 12_2 |
| 卡片库抽查 | 任取五张场景卡复现原结论 | 六字段齐全、判定不为空 | 待填 | 12_3 |

九项全部写"通过"才允许把整体判定记为"通关"。任意一项写"不通过"或"待查"，按最后一列跳回对应小节，补完后再从本表第一行重跑一遍，不做局部补签。

环境适配不改判定口径：未提供 ensurepip 时先备好环境创建工具，或改用带系统站点包的隔离方式；覆盖率数据文件与类型检查缓存若落在对 sqlite 写不友好的卷上，就换到临时目录；构建工具未预装时按 0_3 基线表补齐。

这些只改变"怎么把命令跑起来"，不改变"前缀不同、按锁文件重建、同命令重跑结果一致"这三条通过标准。

"故障演练与回滚"一项不接受"移交部署侧"作为豁免：本地可用 `scripts/rollback_drill.sh` 演完整半程——构建分发产物、装出两份独立副本、在新版本上处理一组输入、把生效目录切回旧版本、逐条比对输出。

线上多实例切换仍属部署侧，但"可导入"与"输入一致"这两条判据在本地就必须拿到实物证据。

### 12_6 常见误区与进阶钩子

「1」误区：把交付当成发版动作。它是"别人能接手"的能力，包含清单、演练与归档。
「2」误区：清单里写"检查配置""确认没问题"。每项必须带命令、预期、判定，能被机器或数值确认。
「3」误区：笔记只记成功结论。反例清单、此路不通清单、待查项才是复盘时最该先看的部分。
「4」误区：以为回滚步骤写完就够了。没演过的回滚等于没有回滚。
「5」误区：把降级当成回滚，或把版本串与构建参数合并成一条证据。降级护单次请求，回滚换整个版本；注入版本要另找启动日志或产物元数据之外的字段，两类证据分开留痕。
「6」全册反模式清单见下表。交付评审时逐行扫一遍，出现任意一条就回到"来源"列补完再重跑；这不是知识测验，是上线前的实物检查。

| 反模式 | 典型症状 | 根因 | 修正动作 | 来源 |
| --- | --- | --- | --- | --- |
| 可变对象作默认参数 | 函数像"记住了上次的值" | 默认值在定义时求值一次 | 用 `None` 占位，在函数体内新建容器 | 4_1 |
| 类属性放可变容器 | 一个实例追加，所有实例都看得见 | 类属性被全体实例共享 | 移到初始化里逐实例新建，或用 `default_factory` | 5_1 |
| 用共享默认值批量建容器 | 每个分组都躺着全部数据 | `fromkeys` 第二参数、`[[ ]] * n` 只求值一次 | 改用推导式，让每次迭代新建对象 | 3_4 |
| 切片当深拷贝 | 改了副本，嵌套层的数据跟着变 | 只复制外层引用，不复制元素对象 | 嵌套结构用 `deepcopy` 或逐层新建，并注明共享到第几层 | 3_1 |
