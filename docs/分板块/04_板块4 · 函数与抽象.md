# Python 语言从入门到精通 · 分板块

## 板块4 · 函数与抽象：参数、闭包、装饰器、生成器与类型注解

### 4_1 核心机理与关键概念

板块3 把数据摆平，板块4 决定"行为怎么被复用而不被复制"。Python 的抽象工具很轻，但轻工具最容易用出隐性副作用。

参数分四类：位置、关键字、仅位置、仅关键字；`*args` 收集多余位置参数，`**kwargs` 收集多余关键字参数。默认值在函数定义时求值一次，这个事实在板块2 已用案例说明。

作用域按 LEGB 顺序查找名称（局部、闭包、全局、内建），闭包会捕获外层名称本身而非当时的值，因此循环里创建的一组函数常会"全都记住最后一次的值"——修法是用默认参数或工厂函数把值当场固定。

装饰器本质是"接收函数、返回函数"，`functools.wraps` 用来保留原函数的名称与文档，否则调试与文档生成都会失真。生成器把"一次算完"改成"要一个给一个"，`yield from` 负责委托给子迭代器，内存占用与数据规模脱钩。

类型注解与 `Protocol` 提供静态可读性：注解不强制运行时行为，但配合类型检查工具能把一批错误挡在运行之前。

```text
  调用方 --> 装饰器包装层 --> 原函数
                 |              |
            计时/日志/缓存   只做一件事
                 |              |
                 +-- wraps 保留身份 --+

  列表推导: [f(x) for x in data]   -> 一次性全量在内存
  生成器  : (f(x) for x in data)   -> 迭代时才逐个产出
```

类型注解的价值不在"给变量贴标签"，而在把约束写成可被检查的契约。常用构件分工明确：

| 构件 | 表达的约束 | 典型用途 |
| --- | --- | --- |
| `TypeVar` | 调用时才确定的类型变量 | 输入输出同型的函数 |
| `Generic` | 类或容器对类型变量参数化 | 自定义容器、可替换实现 |
| `Protocol` | 结构化：只要长得像就满足 | 不引入继承的解耦 |
| `Literal` | 取值只能是列举的字面量 | 状态机、模式开关 |
| `TypedDict` | 字典的键集合与各键类型 | 外部 JSON 契约 |
| `Any` 与 `object` | 放弃检查 / 仅保留最宽上界 | 最后手段，不宜作默认 |

`Any` 与 `object` 的区别常被忽略：前者让检查器对该值放行一切操作，等于局部关闭检查；后者是安全的宽上界，只允许所有对象共有的操作。窄化顺序应是"具体类型、联合、`Protocol`、`object`、`Any`"，反过来写等于把类型检查退化成注释。

闭包捕获的是名称所在的单元格，不是当时的值，这也是 `nonlocal` 能改写外层名称的原因：单元格被多个作用域共享，重新绑定发生在单元格上，所有引用它的闭包一起看见新值。

生成器则是另一条双向通道：`yield` 产出值并挂起，调用方可用 `send` 把值送回成为该表达式的结果，用 `throw` 在挂起点注入异常，用 `close` 触发收尾，`yield from` 再把三者透明委托给子迭代器。

因此生成器不只是"省内存的列表"，而是可暂停、可交互的计算单元。

### 4_3 场景笔记法：函数契约与抽象取舍

抽象层笔记的价值在于"换实现时不翻旧账"，所以用契约卡把隐含约定显性化。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明消费方需要什么能力、当前有哪几个实现或包装层 |
| 预期 | "换实现后调用方零改动；装饰器不丢函数身份；类型检查不报缺失方法" |
| 动作 | 贴出函数签名、装饰器关键行与 `Protocol` 定义 |
| 观察 | 粘贴 `__name__` 输出、类型检查报告首行、内存占用数值 |
| 判定 | 替换成功且身份与类型检查都通过记"通过" |
| 迁移 | "新装饰器先补 wraps；新抽象先问能否用 Protocol 而非基类" |

实用补充：为每个抽象额外记两条"契约外约定"——是否有副作用、是否线程安全。它们不会写进类型系统，却最常在生产里出事，必须落在笔记里。

### 4_4 案例小故事：三个回调全都记住了最后一次

有个批处理界面上放了三个按钮，点击后分别处理三批不同编号的数据。代码用循环一次性创建了三个回调，逻辑看起来干净利落。上线后无论点哪个按钮，处理的都是最后一批编号。

原因是闭包捕获的是外层名称 `batch_id` 本身，而不是创建那一刻的值；循环结束时它早已指向最后一个编号。修法是在创建时把值绑定到回调自己的默认参数里，或者用一个工厂函数当场封住。补的测试也很直接：分别调用三个回调，断言三者结果互不相同。

有意思的是，同一个月里还出了另一件事：有人加了个日志装饰器却漏了 `functools.wraps`，导致监控里所有函数名都变成同一个包装层名字，排障时完全分不清是谁在报错。两件事一起被写进契约卡，标题是"抽象层别把身份弄丢"。

此后评审清单里多了一条：装饰器必须保留原函数身份，闭包必须当场固定值。

### 4_5 实用验证：命令、预期与判定

```python
from functools import wraps

def traced(fn):
    @wraps(fn)
    def inner(*args, **kwargs):
        return fn(*args, **kwargs)
    return inner

@traced
def add(a, b):
    "返回两数之和"
    return a + b

print(add.__name__, add.__doc__)
```

```bash
python -m pytest -q
python -m compileall -q .
```

预期：加上 `wraps` 后 `__name__` 为 `add`、文档串保留；去掉 `wraps` 后两者都变成包装层的信息；三个循环内创建的回调用默认参数固定值后结果互不相同；生成器管道处理大输入时内存占用不随规模线性增长。

判定：做三次主动破坏——删掉 `wraps`、把闭包改回直接捕获循环变量、把生成器改回全量列表，三次都应被测试或可观察数值抓住。全部抓住记"通过"；若某次破坏悄无声息，说明断言或观测有缺口，先补再往下走。

### 4_6 常见误区与进阶钩子

「1」误区：用可变对象作默认参数。改用 `None` 哨兵在函数体内新建。
「2」误区：装饰器不写 `functools.wraps`。调试、文档、某些注册机制都会因此失真。
「3」误区：对有副作用或依赖外部状态的函数加缓存。缓存只适用于输入输出确定的纯函数。
「4」误区：用继承表达"只是长得像"。结构化场景优先 `Protocol`，避免把无关类绑进同一棵继承树。
「5」进阶钩子：写一个既支持迭代又支持 `send` 的生成器，用 `inspect` 查看它的状态，把"挂起—恢复"的观察写成一张假设—反例卡。
