# Python 语言从入门到精通 · 分板块

## 板块10 · 性能与解释器机理：复杂度、剖析、内存与边界

### 10_1 核心机理与关键概念

板块9 保证"改不错"，板块10 保证"改得快且快得有证据"。性能工作最容易走偏的地方，是凭直觉优化一个根本不热的路径。

正确顺序永远是三段式：先测量、再定位、后改动、再测量。测量用 `timeit` 或基准脚本给出耗时与内存基线；定位用 `cProfile` 加 `pstats` 看函数调用次数与累计耗时，用 `tracemalloc` 看内存分配来源；改动只针对定位出的那一处。

解释器侧要理解两件事：引用计数让大多数对象在解绑时即时回收，循环垃圾交给 `gc` 模块处理；对象模型带来的属性字典与装箱成本，使得"选对数据结构"常常比"微调循环写法"收益大得多。板块3 的复杂度表在这里才真正派上用场。

常见有效手段就那么几类：把按值查找换成集合或字典、用生成器替代全量列表、用批量 I/O 替代逐条调用、用缓存复算结果、把热循环里的重复属性查找提出来、必要时把计算密集段交给原生扩展。每一类都必须拿改动前的基线来对照。

```text
  基线测量 -> 剖析定位 -> 单点改动 -> 复测对照 -> 归档数值
     |           |           |           |           |
  timeit     cProfile    只动一处    同样命令    场景卡留存
  tracemalloc  pstats     同输入                 同环境
                 v
       改善不成立 -> 回退改动，保留"此路不通"的笔记
```

再往下一层是字节码与分代回收。`dis` 能把函数反汇编成字节码指令，用来回答"看起来一样的两行代码，为什么多做几次查找"：属性访问、全局名称查找、函数调用在字节码里都是明确指令，热循环里反复做全局查找自然比先绑定到局部变量更贵。

这类优化幅度通常不大，却是看懂剖析结果的基础，也能避免凭语感猜哪行更快。

`gc` 模块管的是引用计数兜不住的部分：对象被分到不同代，新对象更频繁地被检查，活得久的逐步晋升，以此降低扫描成本。由此可推出两条实用判断——互相引用的环会延长存活期，含终结器的对象回收时机更复杂；全局缓存、闭包长引用、注册后未注销的回调，都会让对象比预期活得更久。

观察口径应是"分配速率与存活对象数"，而不是只看某次回收后的总内存。

| 观测工具 | 回答的问题 | 不要拿它回答什么 |
| --- | --- | --- |
| `timeit` | 一小段代码的稳定耗时 | 整条请求链路的瓶颈在哪 |
| `cProfile` 加 `pstats` | 函数调用次数与累计耗时 | 内存分配来自哪一行 |
| `tracemalloc` | 分配位置与峰值 | 对象为何还没被回收 |
| `dis` | 实际生成了哪些字节码指令 | 运行时热点在哪 |
| `gc` 统计 | 各代对象数与回收次数 | 单个对象的确切生命周期 |

测量本身也有口径，读错口径比不测更危险。最常见的是把剖析结果当成绝对耗时：`cProfile` 会给每次函数调用加一层确定性开销，函数多、单次便宜的代码在剖析里显得格外慢，而纯算术循环又显得格外快。

它的用途是排"谁被调得多、谁累计占比高"，不是给最终延迟定值；定值要回到 `timeit` 或端到端基准。

| 口径 | 定义 | 误读后果 |
| --- | --- | --- |
| 墙钟时间 | 含 I/O 等待、调度与锁的真实流逝时间 | 与 CPU 时间混用，把等待当成计算慢 |
| CPU 时间 | 进程实际占用处理器的时间 | 多线程下可能大于墙钟，误判"变慢了" |
| `timeit` 的 number 与 repeat | 每轮执行次数与重复轮数 | 只看单轮，被系统噪声带偏 |
| 取最小值而非平均 | 最快一轮最接近无干扰的真实成本 | 算平均会把偶发调度噪声算进结论 |
| 剖析态耗时 | 插桩后的相对占比 | 当成上线后的绝对延迟 |
| 预热与缓存 | 首次执行含导入、编译与缓存填充 | 把冷启动成本当成热路径成本 |

```text
  端到端墙钟 -> cProfile 定位热点 -> timeit 测单点 -> 复测对照
       |              |                  |              |
    含 I/O 等待    只看相对占比      多轮取最小值    同命令同环境
```

还有一条容易被忽略的纪律：`timeit` 默认会临时关闭垃圾回收，避免回收动作混进计时；因此用基准脚本自测时也要说明是否关闭 GC，否则两次数值不可比。同理，基准函数里必须真正消费计算结果，否则整段逻辑可能被优化掉，得到一条漂亮但为空的基线。

这两条与 9_1 的假断言检查是同一族问题，只是落在解释器侧：看起来全绿，其实什么都没测到。

### 10_2 可落地操作清单

第1步：为热点函数建一张基线表，固定记录输入规模、解释器标识、耗时与内存峰值四项。
第2步：用 `cProfile` 跑一次真实负载，导出统计并按累计耗时排序，找出前三个热点函数。
第3步：用 `tracemalloc` 抓取分配快照，定位分配量最大的代码位置。
第4步：按板块3 的复杂度表检查热路径的数据结构选择，判断是否有"线性查找该换哈希查找"的点。
第5步：只做一处改动（例如把列表查找换成集合），用完全相同的命令与环境复测，算出改善幅度。
第6步：用 `gc` 模块观察一轮回收前后的对象数，记录是否存在存活过久的缓存对象。

### 10_3 场景笔记法：性能基线与改动对照

性能结论必须可复算，所以笔记里"环境条件"与"数值"同等重要。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明负载规模、并发数、解释器与依赖标识、是否关闭其他负载 |
| 预期 | 动手前写"改动后耗时下降且内存峰值不劣化"，不写"应该更快" |
| 动作 | 贴出改动前后的两处代码与完全相同的基准命令 |
| 观察 | 粘贴两轮完整剖析输出与基线数值，保留原始小数位 |
| 判定 | 三轮重复测量趋势一致记"通过"；波动大于改善幅度记"待查" |
| 迁移 | "任何优化提交必须附前后数值；无数值不合并" |

实用补充：单独维护一份"此路不通"清单，记录试过但没改善甚至变差的改动与原因。它比成功清单更值钱，能防止半年后有人把同一个死胡同再走一遍。

### 10_4 案例小故事：核数吃满了，耗时没降

一段纯 Python 的特征统计跑得慢，有人把它拆成八份丢进线程池，监控上机器看着忙了，端到端耗时几乎没变。第一反应是"任务切得不够细"，又加了一倍线程，反而更慢。

按流程跑 `cProfile` 再加一次对照实验才看清：这是纯字节码循环，全局解释器锁让同一时刻只有一个线程在执行，线程池做的只是轮流占用外加切换开销。换成进程池、并把大数组改成"子进程各自加载、只回传精简统计值"之后，耗时才明显下降；而"按线程数继续加码"那套方案被整体回退。

复盘时最被强调的不是那次替换，而是那张基线表：它让"没改善"当场可见。团队由此定下两条规矩——性能改动若拿不出同样命令下的前后数值，评审直接退回；选执行器之前先判定任务属于 I/O 密集还是 CPU 密集，类型判错后面全白做。"此路不通"也要写成卡归档，后来并入板块12 的交付检查单。

### 10_5 实用验证：命令、预期与判定

```bash
python -m timeit -n 100 -r 3 "sum(range(10000))"
python -m cProfile -o profile.out -m mypkg.entry
python -c "import pstats; pstats.Stats('profile.out').sort_stats('cumulative').print_stats(10)"
python -X importtime -c "import mypkg"
python -m pytest -q
```

预期：三轮 `timeit` 数值波动在可接受范围；`pstats` 能明确指出累计耗时最高的函数；`tracemalloc` 快照能对应到具体分配位置；改成集合后耗时下降且内存不劣化；`-X importtime` 输出可读的导入耗时分布；改动后测试仍全绿。

判定：改动前后用同一命令、同一输入规模、同一台机器各跑三轮，取中位数对照。改善方向符合"预期"字段且三轮趋势一致记"通过"。加一道反向验证：把优化改动回退，数值应回到基线附近；回不去说明环境变了或测量有污染，本次结论作废重测。

### 10_6 常见误区与进阶钩子

「1」误区：用一次运行结果下结论。至少三轮取中位数，注意后台负载与缓存预热。
「2」误区：把缓存当万能解药。缓存会延长对象存活期，且对有副作用或输入不稳定的函数有害。
「3」误区：盲目调 `gc` 参数。先看分配来源与存活对象，再决定是否需要干预。
「4」误区：在基准里造一个与真实负载形状完全不同的输入。输入规模与分布必须来自真实场景。
「5」进阶钩子：用 `tracemalloc` 对同一逻辑的列表版与生成器版各抓一份快照，把峰值与分配行数并排写进场景卡，作为"全量 vs 流式"的可复算证据。
