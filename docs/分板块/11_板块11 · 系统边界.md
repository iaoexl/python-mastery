# Python 语言从入门到精通 · 分板块

## 板块11 · 系统边界：外部 I/O、重试退避、配置与优雅退出

### 11_1 核心机理与关键概念

板块10 把单机内部调顺，板块11 处理程序与"不受自己控制的世界"之间的那圈边界。这圈边界的关键词不是性能，而是不确定性。

外部 I/O 会超时、会半途失败、会返回畸形数据，因此每处边界都要回答四个问题：多久算超时、失败是否重试、重试是否幂等、彻底失败如何降级。重试必须配退避（固定间隔或指数退避加抖动），否则下游抖动会被放大成重试风暴；幂等靠请求标识或业务唯一键保证，否则重试就是重复写入。

板块8 的取消机制在这里成为统一总线：超时与取消要能从入口一路传到最外层调用。

优雅退出是另一半：收到终止信号后，先停止接收新任务，再等在途任务在宽限期内收敛，最后释放连接与句柄。配置与密钥走环境变量或外部文件，真实值不进版本库，样例与真实分离，缺项时程序给出明确报错而不是默默用默认值。健康分为存活与就绪两种，就绪探针要真实反映依赖状态。

可观测性靠结构化日志、指标与请求标识串联——日志里没有请求标识，排障就等于在黑屋里找开关。

证书信任包、安装器与基础镜像属于运行环境的一部分。这类变更不改变业务代码，却会改变 TLS 客户端能否安全连上外部服务，因此要单独列为一次故障注入项；所有存量虚拟环境也要逐个核对，不能只验当前激活的那一个。

```text
  入口 -> 上下文(超时/请求标识) -> 外部调用
                 |                    |
                 |              +-----------+
                 |              | 超时/失败 |
                 |              +-----+-----+
                 |                    v
                 |          退避重试(幂等) -> 降级/返回
                 v
  信号 -> 停止接新 -> 等待在途(宽限期) -> 释放资源 -> 退出
```

四问表之外还有一层更贴 Python 工程现实的判断：**配置从哪来、缺了怎么办**。配置优先级一旦没写清，"本地能跑、线上用了另一套值"就成了常态。

```text
  内置默认值 -> 配置文件 -> 环境变量 -> 显式启动参数
       |            |            |            |
    最低优先     便于本地     容器/CI 常用   最高优先
       |
       +-- 必填项无值时: 启动即报错，不静默用默认
       +-- 样例文件只放占位值，不进真实密钥
```

| 配置项 | 放哪里 | 判定口径 |
| --- | --- | --- |
| 下游地址与超时 | 环境变量或配置文件 | 缺项时明确报错，不拼一个"看起来能用"的地址 |
| 密钥与凭据 | 外部注入，只读 | 样例文件不含真实值，日志里不打印 |
| 特性开关 | 显式参数或环境变量 | 能说明"关掉之后走哪条分支" |
| 地区与时区规则 | 配置 + 标准时区库 | 与板块7 的带时区表示一致，不手算偏移 |

"彻底失败如何降级"也不能只写"返回兜底"，要写清兜底是哪一种，因为不同形态的数据一致性代价完全不同：

| 降级形态 | 用户看到什么 | 适用条件 | 代价 |
| --- | --- | --- | --- |
| 返回空结果 | 空列表并标注"暂不可用" | 只读展示，允许短暂陈旧 | 可能被误当成"确实没有数据" |
| 返回最近一次成功缓存 | 旧数据加时间戳 | 读多写少、允许陈旧 | 要标明数据时刻，否则误导 |
| 返回可解释的错误 | 明确原因与重试建议 | 写操作、涉及一致性 | 用户体验最差，但语义最诚实 |
| 转入排队后续处理 | 已受理、稍后通知 | 可异步完成且能去重 | 需要幂等键与状态可查 |

写操作通常不该"兜底成功"：与其返回一个看似成功的假结果，不如明确失败并让用户决定是否重试。幂等键在这里同时服务两处——重试时避免重复写入，排队后查询状态时能定位同一笔请求。

优雅退出同样要分阶段记录，否则"收到信号就退出"和在途任务被硬掐断之间没有可观测的差别：

| 阶段 | 该做的事 | 记进场景卡的观察 |
| --- | --- | --- |
| 收到信号 | 停止接新，标记不再健康 | 信号类型与接收时刻 |
| 在途收敛 | 等待任务组取消或完成 | 在途数量归零耗时 |
| 资源释放 | 关闭连接、句柄与线程池 | 关闭前后句柄数 |
| 进程退出 | 明确退出码 | 退出码与总关闭耗时 |

### 11_2 可落地操作清单

第1步：给每个外部调用列一张四问表，并把降级形态写成具体一种（空结果、带时间戳的缓存、可解释错误、排队受理），不写"返回兜底"这种模糊项。
第2步：实现带指数退避与抖动的重试，写清初始间隔、乘数、上限与总耗时；只对暂时性失败重试，参数与鉴权错误直接返回。
第3步：为一个写操作加上请求标识，由入口生成、按业务唯一键去重，重复提交返回首次结果；排队场景用同一键可查询状态。
第4步：注册终止信号处理，按"停止接新—在途收敛—释放资源—明确退出码"四阶段记录耗时。
第5步：把存活探针与就绪探针分开；就绪探针真实检查依赖，存活探针只判本进程是否卡死，避免下游抖动触发全体重启。
第6步：把配置改成"默认值—文件—环境变量—显式参数"四级优先，提交一份不含真实值的样例，删除必填项后确认启动即报清晰错误。

### 11_3 场景笔记法：边界故障与降级演练

边界类知识只能靠"故意制造故障"来验证，所以笔记要按故障注入项组织。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明注入的故障类型：延迟、断连、畸形响应、依赖不可用、信任链或基础层变更、终止信号、缺失配置 |
| 预期 | "超时内返回；重试次数不超上限；重复请求结果一致；退出时在途任务收敛" |
| 动作 | 贴出故障注入方式、退避参数、宽限期与探针代码 |
| 观察 | 粘贴耗时、重试次数、返回码、日志里的请求标识链、退出耗时，以及信任链核对的原始输出（证书链验证结果、镜像 digest、逐环境前缀清单） |
| 判定 | 预期四项逐条达标记"通过"，任一不达标保留现场并标"待查" |
| 迁移 | "每新增一个外部依赖，补一行四问表与一个故障注入用例" |

实用补充：建一份"故障演练清单"，把注入过的故障逐条打勾。没被注入过的边界等于没验证过，这条判据在板块12 的总验收里会再出现一次。

### 11_4 案例小故事：业务代码没动，安装全失败了

一次例行重建后，几个服务的依赖安装集体报证书校验失败，而仓库里没有任何代码改动，上一版产物还是好的。排查先排除了下游服务：连的是同一个包索引，故障只出现在部分机器上。

根因在环境不在代码：证书信任链轮换之后，有些机器沿用旧的基础镜像层，有些存量虚拟环境里的包管理器还是旧版本，握手时对不上新的信任基础。更麻烦的是团队只验了"当前激活的那一个环境"，另外几个由定时任务使用的环境一直没被清点。

整改按四个动作落地：核对解释器是否仍在官方支持范围内，已终止支持的分支列迁移待办；逐个清点所有存量虚拟环境并更新工具链与证书相关依赖；重建容器镜像时显式拉取基础镜像并按 digest 核对，再禁用层缓存重建。

把每次核对的本地输出贴进场景卡，判定只写"与官方当前说明一致"或"待迁移"，不抄公告里的具体版本。验证方式是故意用旧层构建一次，确认门禁会拒绝它。

复盘时四问表补了新的一列："信任基础变了，代码要不要改"。答案是通常不用，但验证动作必须重跑。从那以后边界设计不再只讨论"怎么调成功"，也会讨论"代码没动时哪些前提会变"。这份清单后来成了板块12 交付评审的必备附件。

### 11_5 实用验证：命令、预期与判定

```bash
python -m pytest -q
python -m pytest -k "boundary or shutdown" -v
python -m mypkg.entry &
kill -TERM $!
```

预期：慢下游场景下请求在约定超时内返回且重试次数不超过上限；同一请求标识重复提交只产生一条记录；终止信号后服务停止接新、在途任务在宽限期内收敛、进程正常退出；就绪探针在依赖不可用时返回非就绪状态；删除必填配置项后程序给出明确报错；禁用层缓存重建后外部调用可正常建立，门禁测试全绿。

判定：逐项对照四问表与故障演练清单，各项全过记"通过"。加两道破坏性验证：把退避去掉、只保留立即重试，在同样的慢下游下重试次数应显著上升甚至触发限流；用旧的基础镜像层重建一次，信任基础相关的检查应明确拒绝或标记"待迁移"。

两处对照都看得到，才能说明退避与信任链核对确实在起作用，而不是恰好下游恢复了。

### 11_6 常见误区与进阶钩子

「1」误区：重试不加抖动。多个实例同时退避会同步化，形成周期性冲击。
「2」误区：把真实配置或密钥提交进版本库。用环境变量或外部文件，配一份不含真实值的样例。
「3」误区：就绪探针永远返回成功。它必须反映依赖状态，否则流量会被导到还没准备好的实例。
「4」误区：收到终止信号直接退出，不等待在途任务。要设宽限期并按四阶段记录耗时与退出码。
「5」误区：四问表里把降级写成"返回兜底"。要指明是哪一种形态、用户看到什么、数据一致性代价是什么；写操作通常应明确失败而非兜底成功。
「6」误区：配置必填项缺失时静默用默认值，或把真实密钥写进样例文件。启动即报错、样例只放占位值。
「7」误区：把依赖可用性检查塞进存活探针，或对确定性失败也重试。前者会把局部抖动升级成全体重启，后者只是放大无效流量。
「8」误区：幂等键由下游生成或用时间戳拼成。同一业务请求重试两次会拿到两个键，去重与状态查询双双失效。
「9」进阶钩子：给结构化日志加一个采样开关，在高流量下对比全量日志与采样日志的 CPU 开销，把数值写进场景卡，作为板块10 剖析流程的真实负载案例。
