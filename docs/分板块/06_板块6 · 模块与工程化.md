# Python 语言从入门到精通 · 分板块

## 板块6 · 模块与工程化：导入机制、包结构与依赖锁定

### 6_1 核心机理与关键概念

板块5 让单个模块内聚，板块6 让一堆模块能被别人、被另一台机器、被 CI 稳定地重建出来。核心只有一句话：把"我这里能跑"变成"哪里都能跑"。

导入不是文本包含，而是一次带缓存的执行：解释器按 `sys.path` 找模块，找到后执行其顶层代码，把结果放进 `sys.modules`；后续同名导入直接取缓存。由此推出三条工程约束——模块顶层不要有副作用，循环导入往往源于顶层就互相取用，相对导入只在包内有效且依赖"以包方式启动"。

项目布局有一个被广泛验证的收敛形状：`src/` 放包源码，测试放在包外，配置与元数据集中在项目根的一份声明文件里；采用 `src` 布局能逼你以"已安装"的形态测试，而不是靠当前目录碰巧可导入。依赖侧要区分"声明需要什么"与"锁定确切装了什么"：前者给人看，后者给机器复现。

版本号、构建产物元数据与入口声明都写进同一份项目配置，避免散落。

```text
  项目根
  +-- pyproject / 项目配置     声明元数据、依赖、入口
  +-- src/
  |    +-- mypkg/
  |         +-- __init__.py
  |         +-- core.py
  +-- tests/
  +-- 锁文件                   确切版本，供干净环境重建

  导入链路: sys.path -> 找到模块 -> 执行顶层代码 -> sys.modules 缓存
                              |
                         副作用在此发生，所以要克制
```

`sys.path` 只是查找起点，后面还有一套可插拔的查找器与加载器：路径条目逐个交给查找器，命中后由加载器执行模块代码并生成模块对象，`sys.modules` 是这条链的缓存。`importlib` 把这套机制暴露出来，既能按名字动态导入或重新加载，也能按规格构造模块。

插件系统、按配置选择实现、测试里受控替换模块这三类需求都应走它，比手工改 `sys.path` 字符串更可控。

包的形态有两种。常规包由 `__init__.py` 标记，该文件本身就是包的初始化模块，首次导入包时执行，适合放公开的再导出与包级约定，但不宜塞重逻辑。没有该文件的目录仍可形成命名空间包，其路径片段可分散在多个位置并由导入系统合并。

代价是包级初始化代码无处安放。两种形态混用时，最容易出现"本地能导入，打包后某个子包消失"。

| 概念 | 职责 | 误用后果 |
| --- | --- | --- |
| `sys.path` | 提供查找起点 | 靠脚本目录碰巧命中，换启动方式即失效 |
| 查找器与加载器 | 定位并执行模块代码 | 手写路径拼接绕过导入系统，缓存行为不一致 |
| `sys.modules` | 缓存已加载模块 | 测试里直接改它做替换，污染后续用例 |
| `importlib` | 按名字或规格可控地加载 | 用动态执行拼模块名，导入来源无法追踪 |
| `__init__.py` | 常规包的初始化与再导出 | 塞入连接、读配置等副作用 |
| 命名空间包 | 跨位置合并同名包目录 | 误以为包级初始化一定会执行 |

### 6_2 可落地操作清单

第1步：把包源码迁到 `src/` 布局，在干净目录里验证"不安装就导入失败、按可编辑方式安装后导入成功"。
第2步：打印 `sys.modules` 中自己包的键，确认同一模块只被执行一次，并在顶层放一行打印作为证据。
第3步：制造一次循环导入，记录报错首行；再用"把取用挪到函数内"或"抽第三方模块"两种方式各解一次。
第4步：把宽松的依赖声明写进 `requirements.txt`，把 `python -m pip freeze` 的确切版本输出保存到 `requirements.lock`，逐行解释两份文件的差异。
第5步：在项目配置里声明一个命令行入口，安装后直接敲命令名启动，不再依赖脚本路径。
第6步：构建一次分发产物，检查产物元数据里的包名、版本与依赖是否与声明一致。

### 6_3 场景笔记法：导入与依赖决策留痕

依赖类问题的复盘难点是"当时为什么选它、为什么这样放"，所以用决策卡把取舍留痕。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明要解决的问题、候选依赖、当前依赖图状态、包布局调整 |
| 预期 | "锁定重建结果一致；导入链无循环；产物元数据与声明一致" |
| 动作 | 贴出安装、锁定生成、构建与导入验证的原始命令 |
| 观察 | 粘贴循环导入报错首行、锁定文件差异摘要、产物元数据 |
| 判定 | 每条差异都有解释记"通过"，出现"不知道哪来的"记"待查" |
| 迁移 | "新增依赖前先写一张卡：它替我解决什么、去掉它要写多少代码" |

实用补充：把 `sys.path` 与 `sys.modules` 的关键输出裁成三行摘要存进笔记，不必全文归档；但每次布局调整后都要重贴一次，便于横向对照。

### 6_4 案例小故事：本地全绿、CI 全红的那个包

团队合并了一个看起来无害的改动：把两个模块挪了位置，顺手把其中一个的相对导入改成了绝对导入。本地用 `python src/mypkg/core.py` 直接跑，一切正常；CI 以包方式安装后运行，立刻报导入错误。

查下来是两步叠加：直接跑脚本时 `sys.path` 首位是脚本所在目录，包上下文根本没建立，相对导入必然失效；同时有人把初始化逻辑写在模块顶层，CI 收集测试时被执行了一次，触发了本该由入口才做的连接动作。本地因为恰好先跑过入口，缓存掩盖了顺序问题。

修复不涉及业务逻辑：统一改成 `python -m mypkg...` 方式启动，把顶层副作用收进入口，测试改为在干净环境按安装形态收集。CI 里再加一道"锁定文件重建后差异必须为空"的检查。后来这道检查又抓到过一次被悄悄升级的间接依赖。

大家把那张决策卡命名为"不要靠当前目录碰巧能导入"，一直贴到板块12 的交付清单里。

### 6_5 实用验证：命令、预期与判定

```bash
python -m pip freeze
python -m pip check
python -c "import mypkg; print(mypkg.__file__)"
python -c "import sys; print(sys.modules.get('mypkg'))"
python -m build   # 需先安装构建工具，见 0_3 的工具前提说明
python -m pytest -q
```

预期：`pip check` 报告依赖无冲突；`mypkg.__file__` 指向已安装包路径而非源码脚本路径；`sys.modules` 中该包键存在且顶层副作用未重复执行；构建产物元数据与项目声明一致；测试在干净环境全绿。

判定：取"干净环境重跑"为准——新建空目录、只按锁定文件安装、不复用本机站点包，重跑 `python -m pytest -q`，结果一致记"通过"。再加一道破坏性验证：故意在模块顶层放一行会抛异常的代码，测试收集阶段应立即失败。

能复现这个失败，说明"顶层副作用"确实被门禁看见，而不是碰巧没触发。另核对工具链与证书信任基础是否随基础环境更新：容器场景禁用层缓存重建后复跑同一套命令，功能一致但信任基础未更新的，不记"通过"。

### 6_6 常见误区与进阶钩子

「1」误区：用脚本路径直接启动包内模块。改用 `python -m 包名.模块`，让包上下文成立。
「2」误区：把初始化、连接、读配置写在模块顶层。用入口函数与 `if __name__ == "__main__":` 守住。
「3」误区：只留宽松声明不留锁定版本。干净环境会被悄悄升级，问题往往隔很久才暴露。
「4」误区：靠当前目录可导入就以为打包没问题。`src` 布局加安装形态测试能提前暴露。
「5」进阶钩子：用 `python -X importtime -c "import mypkg"` 观察导入耗时分布，找出最慢的一层，把数值与优化前后对照写进决策卡。
