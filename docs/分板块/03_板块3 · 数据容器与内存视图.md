# Python 语言从入门到精通 · 分板块

## 板块3 · 数据容器与内存视图：列表、字典、集合、切片与拷贝

### 3_1 核心机理与关键概念

板块2 说明"名称贴在对象上"，板块3 说明"一批对象怎么组织"。选容器的本质是在时间复杂度与语义之间做取舍，而不是看哪个写起来短。

列表是动态数组：按下标访问与尾部追加都很便宜，中间插入删除要搬移元素；容量按需扩增，单次扩容成本被后续多次追加摊薄。字典与集合基于哈希表：按键平均常数时间查找，代价是键必须可哈希、内存开销更大、最坏情况会退化。元组不可变，可当字典键，也常用于表达"一组位置固定的字段"。

切片返回新列表（或新元组），但只复制引用，不复制元素对象——这正是浅拷贝与深拷贝的分水岭。

内存侧还有一层：CPython 以引用计数为主、循环垃圾回收为辅。对象每被绑定一次计数加一，解除绑定减一，归零即回收；但互相引用的环需要循环检测器处理。理解这一点，才能解释"为什么闭包或缓存会让对象活得比预期久"。

```text
  original = [[1], [2], [3]]
  shallow = original[:]        deep = copy.deepcopy(original)

  shallow ---> [ ref0, ref1, ref2 ] ---> 同一批子列表
  deep    ---> [ ref0', ref1', ref2' ] ---> 新建的子列表副本

  改 shallow[0][0] -> original[0] 跟着变
  改 deep[0][0]    -> original[0] 不受影响
```

常用操作复杂度速查如下。它回答的是"数据规模涨十倍时，哪一步会先撑不住"，板块10 会拿它做真正的性能判定。

| 容器 / 操作 | 代价量级 | 判定要点 |
| --- | --- | --- |
| 列表按下标取值、尾部追加 | 常数级 | 扩容成本被后续追加摊薄，单次慢不代表整体慢 |
| 列表按值查找、头部插入 | 线性级 | 高频按值查找应换集合或字典 |
| 列表中间插入删除 | 线性级 | 需要搬移后续元素 |
| 字典 / 集合按键存取 | 平均常数级 | 键必须可哈希，最坏情况会退化 |
| `deque` 双端进出 | 常数级 | 单端队列别用列表硬扛 |
| `heapq` 入堆与出堆 | 对数级 | 只取最值时不必整体排序 |
| 全量排序 | 线性对数级 | 只需前几个元素时考虑更窄的选择 |

还有一层容易被忽略的是**视图与副本**。切片会新建容器对象，但元素仍是对原对象的引用；`memoryview` 则连数据都不复制，只是给同一块缓冲区换一个观察窗口。因此处理大块字节时，视图能省下整份拷贝，但也意味着"改视图即改原缓冲区"。

| 写法 | 是否新建容器 | 是否复制元素对象 | 改动是否影响原数据 |
| --- | --- | --- | --- |
| 切片 `s[:]` | 是 | 否 | 改元素内容会，替换某格不会 |
| `copy.copy` | 是 | 否 | 同切片，共享到外层为止 |
| `copy.deepcopy` | 是 | 是（递归） | 否 |
| `memoryview` | 否，是视图 | 否，共享缓冲 | 会，且原缓冲区立刻可见 |
| 推导式 `[x for x in s]` | 是 | 否，元素仍是原引用 | 改元素内容会；只有表达式里显式构造才新建元素 |

把"共享到第几层"写成一句可判定的话，比背容器名词有用：切片共享到元素对象，`deepcopy` 不共享，`memoryview` 连容器都不新建。3_3 的场景卡要求画出动作前后两张草图，画的就是这一列。

### 3_2 可落地操作清单

第1步：对同一嵌套列表分别做切片、`copy.copy`、`copy.deepcopy`，修改第一层子列表元素后打印三者，确认哪一层共享。
第2步：给列表做尾部追加与头部插入各若干次并计时，把量级差异写进笔记，不要求精确数值。
第3步：用不可哈希对象当字典键触发一次报错，再用元组与自定义可哈希对象各成功一次。
第4步：构造一个互相引用的环，用 `gc` 模块观察回收前后的对象数，确认循环垃圾由检测器处理。
第5步：对一份字节数据分别用切片与 `memoryview` 取子区间，比较是否产生整份复制。
第6步：用 `deque` 与 `heapq` 各实现一次队列类需求，记录各自适合的场景。

### 3_3 场景笔记法：容器选择与拷贝深度记录

容器类问题看不到引用关系就记不住，所以笔记必须以"草图 + 身份标识"为证据。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明数据规模、嵌套层数、触发动作是切片、浅拷贝还是深拷贝 |
| 预期 | 动手前画出两张草图：动作前的引用关系与动作后的引用关系 |
| 动作 | 贴出打印 `id()` 与内容的最小片段 |
| 观察 | 粘贴实际身份标识与元素值，标识原样保留 |
| 判定 | 草图与观察一致写"证实"，不一致标出具体哪一层判断错了 |
| 迁移 | "凡函数返回容器或子区间，注释里写明共享到第几层" |

实用补充：给每个容器实验配一条"破坏性验证"——把嵌套层数加一层或把数据类型从不可变换成可变再跑一次，看结论是否翻转。能翻转的才是真规律。

### 3_4 案例小故事：所有分组都拿到了同一个空列表

某报表要按地区把订单分组，开发用一行 `groups = dict.fromkeys(regions, [])` 建好容器，再逐个 `groups[r].append(order)`。跑出来每个地区下面都躺着全部订单，总量翻了地区数那么多倍，却没有一条报错。

原因不在 `append`，而在建容器那一行：`fromkeys` 的第二个参数只求值一次，所有键共享同一个列表对象。它和板块2 里"可变默认参数"是同一族问题，只是藏在标准库 API 的默认值语义里，审起来更像"我明明初始化过了"。改成字典推导让每次迭代新建列表，问题当场消失。

补的测试刻意只建两个键：往第一个键追加一条，断言第二个键仍为空、且两个列表不是同一对象。团队由此把口径从"共享还是复制"细化成"每个键是否各自持有独立对象"，写进 4_3 的契约卡。

12_6 的反模式清单里也多了一条"用共享默认值批量建容器"。这类 bug 不抛异常、不写日志，只把数据悄悄叠在一起。

### 3_5 实用验证：命令、预期与判定

```python
import copy
original = [[1], [2], [3]]
shallow = original[:]
deep = copy.deepcopy(original)
shallow[0][0] = 99
print(original, shallow, deep)
```

```bash
python -m pytest -q
python -c "import gc; print(gc.isenabled())"
```

预期：`original` 与 `shallow` 的第一格都变为 99，`deep` 保持原值；把修改改成外层替换 `shallow[0] = [9]` 时 `original` 不受影响；`gc.isenabled()` 输出为 True 时循环检测器在工作。

判定：把两条修改路径的输出逐条与草图对照，全中记"通过"。再加一道破坏性验证：把嵌套换成不可变元组，重复同样的浅拷贝修改路径，观察是否还能改到内部；能看到这个翻转，说明你真的掌握了"复制的是引用而非元素"。

### 3_6 常见误区与进阶钩子

「1」误区：把切片当深拷贝。嵌套结构必须显式 `deepcopy` 或逐层新建。
「2」误区：用列表做"按值频繁查找"的主结构。换成集合或字典，先用复杂度表判断。
「3」误区：往字典里塞可变对象当键。键必须可哈希且哈希值在生命周期内稳定。
「4」误区：以为引用计数归零就一定立刻释放。含 `__del__` 的环或跨解释器差异会改变时机，以 `gc` 观察为准。
「5」误区：用 `dict.fromkeys(keys, [])` 或乘法 `[[ ]] * n` 批量建容器。第二个操作数只求值一次，所有键或所有行共享同一对象；改用推导式让每次迭代新建。
「6」误区：把 `copy.copy` 当成"只复制一层所以够用"。要写清复制到第几层，并在测试里断言被跳过的那一层是否仍共享。
「7」进阶钩子：用 `sys.getsizeof` 分别量一个列表、一个字典与一个元组在相同元素数下的占用，把数值与"为什么字典更大"写进场景卡。
