# Python 语言从入门到精通 · 分板块

## 板块12 · 生产交付、反模式清单与通关总验收

### 12_1 核心机理与关键概念

前面十一个板块各自交付一种能力，板块12 把它们合成一次"能被别人接手"的交付。判断标准不是"我机器上跑通了"，而是"另一个人在干净环境里，按一份清单，能重建、能验证、能回滚"。

一次完整交付包含五层：可复现构建（锁定依赖、固定解释器视图、产出带元数据的分发产物）、配置与密钥（外部注入、样例与真实分离）、可观测性（结构化日志、指标、请求标识）、安全网（门禁全绿、故障演练清单、回滚步骤）、知识归档（所有场景卡可检索、例外有理由）。这五层缺一层，交付就依赖某个人的记忆。

同样重要的是把全册笔记收口。前面各板块留下了不同形态的记录：资料取用卡、环境快照卡、假设—反例卡、引用草图、契约卡、状态卡、依赖决策卡、字段契约表、退出条件表、断言意图卡、性能基线表、故障演练清单。它们不该散在各处，而应汇成一个可按场景检索的卡片库，并配一份索引。

```text
  可复现构建   配置与密钥   可观测性   安全网   知识归档
      |            |           |          |          |
      +------------+-----------+----------+----------+
                           v
                 干净环境按清单重建
                           v
              门禁全绿 + 故障演练通过 + 可回滚
                           v
                     才叫"交付完成"
```

**可回滚性：降级不等于回滚**

交付五层里写了"能回滚"，但不少团队把两件事混成一件：**降级**是依赖坏了仍给一个可解释的响应，**回滚**是把正在运行的代码换回上一版。前者保护单次请求，后者保护整个版本，判据互不通用。

| 维度 | 降级 | 回滚 |
| --- | --- | --- |
| 触发条件 | 下游超时、返回异常、限流 | 新版本上线后门禁或导入校验不达标 |
| 作用范围 | 一次请求或一段时间窗 | 整个已安装版本 |
| 状态要求 | 允许返回带时间戳的旧结果 | 必须能读回新版本已写入的输入 |
| 结束方式 | 依赖恢复后自动收敛 | 显式切换生效目录并复跑门禁 |
| 验收判据 | 响应可解释、不静默给空 | 已安装形态可导入、同一输入输出一致 |

要让回滚真的能演，分发产物先得满足四条判据：

| 判据 | 含义 | 破坏它的做法 |
| --- | --- | --- |
| 版本可辨识 | 分发产物元数据可读出确切版本 | 所有构建都叫同一个名字 |
| 配置外置 | 切换版本不需要改配置内容 | 把版本相关配置写进产物内部 |
| 状态兼容 | 旧版本能读回新版本写过的输入 | 只做向前兼容、不做向后兼容 |
| 切换原子 | 保留上一版安装副本，切换失败可立刻指回 | 就地覆盖站点包，没有可回退副本 |

四条里最常漏的是第三条。只验"包能导入"、不验"新版本处理过的输入在旧版本上结果一致"，等于只演了半程。12_5 因此要求"服务恢复"与"数据无损"同时成立，实战工程的 `scripts/rollback_drill.sh` 把这两项落成可重跑的命令。

### 12_2 可落地操作清单

第1步：整理一份交付清单，逐项写明命令、预期输出、判定人，不写"检查一遍"这种模糊项。
第2步：在干净环境里只凭清单重建虚拟环境、安装锁定依赖并跑门禁；容器构建显式拉取基础镜像并按 digest 核对、再禁用层缓存重建，另清点所有存量虚拟环境的工具链支持状态，把每一步输出贴进交付记录。
第3步：核对配置与密钥：真实值不在版本库，样例可独立启动，缺项时程序给出明确报错。
第4步：跑一遍故障演练清单，逐条打勾，未演练过的边界补一个注入用例。
第5步：跑回滚演练脚本实演一次：从新版本切回上一版安装副本，同时验可导入与同一组输入输出一致。分发产物元数据单独核对，不靠目录名认版本；线上多实例切换另按 0_2 边界声明处理。
第6步：把全册场景卡按"场景类型"归档，建一份索引，确保每张卡的六字段完整、判定不为空。

### 12_3 场景笔记法：全册复盘与跨场景归档

这是全册笔记的收口方法，目标是把"学过的东西"变成"查得到的东西"。

| 字段 | 本场景填写要求 |
| --- | --- |
| 场景 | 写明复盘范围（哪几个板块、哪次交付演练） |
| 预期 | "任意一张卡能在索引里一步定位；六字段无空缺；每个待查都有结论" |
| 动作 | 贴出归档目录结构与索引生成方式 |
| 观察 | 粘贴卡片总数、待查项数量、被推翻假设数量、性能改善数值清单 |
| 判定 | 抽查五张卡均能复现原结论记"通过" |
| 迁移 | "每完成一个阶段，重跑一次归档检查，而不是等全部结束" |

**回滚演练卡的六字段填写要求**（第十一类专用，其余十一类沿用各板块 X_3 的模板）

| 字段 | 回滚演练卡填写要求 |
| --- | --- |
| 场景 | 写明两份安装副本、切换判据、本次输入样本 |
| 预期 | 旧版本在已安装形态下可导入，且同一组输入输出一致 |

| 迁移 | 每次发版前重跑一次演练，记录随产物一起归档，不单独留在个人笔记里 |

**晋级判定卡的六字段填写要求**（第十二类专用，其余十一类沿用各板块 X_3 或本节的专用模板）

| 字段 | 晋级判定卡填写要求 |
| --- | --- |

### 12_4 案例小故事：故障复盘时，找不到那张基线卡

一次线上延迟抖动需要快速判断"能不能先回滚"，值班的人翻遍仓库和聊天记录，只找到一句"上次优化过，快了不少"，没有前后数值、没有当时的负载规模，也没人记得那次改动是否动过数据结构。回滚决策因此拖了很久，最后靠重新压测才敢动手。

问题不在代码，在知识归档。那张性能基线表留在个人笔记里没进卡片库，环境快照卡、依赖决策卡也散在不同地方，索引从来没建过。程序本身一直是好的，但"判断依据"没有跟着程序一起交出去。

补齐的方式不是补文档，而是补"可检索"：全部场景卡按十二类归档，索引里逐类记用途、来源小节与最后复核；环境快照卡、依赖决策卡、性能基线表各自归位，判定为"待查"的卡单独置顶。索引本身进版本库，随每次交付演练一起更新，不再躺在个人笔记里。

验收口径也跟着改了：让一位没参与过开发的人只凭清单和索引，在干净环境重建、跑门禁、调出当时的基线卡对照当前数值，再据此决定回滚。"第三方能不能找到判断依据"成了交付检查单的最后一项。

那次复盘后写在笔记首页的话是：程序跑得起来，只说明它能用；判断依据查得到，才说明它敢改。板块1 里那条"能跑不等于在正确的环境里跑"，到这里补上了另一半。

### 12_5 实用验证：命令、预期与判定

```bash
python -m venv .venv
. .venv/bin/activate   # 类 Unix；Windows 改用该环境 Scripts 目录下的激活脚本
python -m pip install -r requirements.lock
python -m pip check
python -m pytest -q
python -m pytest --cov=mypkg --cov-report=term-missing -q   # 需覆盖率插件，见 0_3
python -m compileall -q .
python -m build   # 需构建工具，见 0_3
```

预期：干净环境按锁定文件安装后 `pip check` 无冲突；测试全绿且覆盖率报告能列出薄弱行；`compileall` 无语法错误；构建产物元数据与项目声明一致；故障演练清单逐项打勾；回滚演练后服务恢复且数据无损；抽查五张场景卡均能复现原结论。

判定：这是全册唯一一次"全项验收"，采用一票否决——上列任何一项不达标，整体记"未通过"，回到对应板块补完再重跑。全部达标后，在索引里把本次验收的命令、输出摘要与判定写成最后一张卡，命名"通关记录"。此后每次重大改动，只需重跑这份清单，不必重读全册。

"全项"必须落到能逐行打勾的载体上，否则一票否决只是句口号。下表随交付清单一并打印，"现场判定"列由执行人手写"通过 / 不通过 / 待查"，不预填、不事后补。

| 验收项 | 命令或动作 | 通过标准 | 现场判定 | 不达标回到 |
| --- | --- | --- | --- | --- |
| 隔离环境 | 新建虚拟环境并打印解释器前缀 | 前缀指向新环境而非系统目录 | 待填 | 0_3 |
| 锁定安装与依赖冲突 | 按锁文件安装后执行 `python -m pip check` | 无冲突，清单可逐行解释 | 待填 | 6_5 |
| 语法与导入 | `python -m compileall -q .` 并以包方式启动入口 | 无语法错误，不靠脚本目录碰巧可导入 | 待填 | 6_1 |
| 测试与随机顺序 | 门禁脚本加一轮顺序扰动 | 两种顺序结果一致，无状态耦合 | 待填 | 9_5 |
| 覆盖率薄弱行 | 生成含未覆盖行号的报告 | 能定位到具体行，最低的两个模块各有边界用例 | 待填 | 9_3 |
| 产物元数据 | 干净环境构建并读取分发产物元数据 | 与项目声明一致 | 待填 | 6_5 |
| 信任链与基础层 | 禁用层缓存重建并复跑门禁 | 与官方当前说明一致，旧层被明确拒绝 | 待填 | 11_3 |
| 故障演练与回滚 | 跑 `scripts/rollback_drill.sh`：两份副本切换、逐行比对、旧版本复跑门禁 | 注入项全覆盖；可导入与输入一致，输出演练通过标记 | 待填 | 12_2 |
| 卡片库抽查 | 任取五张场景卡复现原结论 | 六字段齐全、判定不为空 | 待填 | 12_3 |

九项全部写"通过"才允许把整体判定记为"通关"。任意一项写"不通过"或"待查"，按最后一列跳回对应小节，补完后再从本表第一行重跑一遍，不做局部补签。

环境适配不改判定口径：未提供 ensurepip 时先备好环境创建工具，或改用带系统站点包的隔离方式；覆盖率数据文件与类型检查缓存若落在对 sqlite 写不友好的卷上，就换到临时目录；构建工具未预装时按 0_3 基线表补齐。

这些只改变"怎么把命令跑起来"，不改变"前缀不同、按锁文件重建、同命令重跑结果一致"这三条通过标准。

"故障演练与回滚"一项不接受"移交部署侧"作为豁免：本地可用 `scripts/rollback_drill.sh` 演完整半程——构建分发产物、装出两份独立副本、在新版本上处理一组输入、把生效目录切回旧版本、逐条比对输出。

线上多实例切换仍属部署侧，但"可导入"与"输入一致"这两条判据在本地就必须拿到实物证据。

### 12_6 常见误区与进阶钩子

「1」误区：把交付当成发版动作。它是"别人能接手"的能力，包含清单、演练与归档。
「2」误区：清单里写"检查配置""确认没问题"。每项必须带命令、预期、判定，能被机器或数值确认。
「3」误区：笔记只记成功结论。反例清单、此路不通清单、待查项才是复盘时最该先看的部分。
「4」误区：以为回滚步骤写完就够了。没演过的回滚等于没有回滚。
「5」误区：把降级当成回滚，或把版本串与构建参数合并成一条证据。降级护单次请求，回滚换整个版本；注入版本要另找启动日志或产物元数据之外的字段，两类证据分开留痕。
「6」全册反模式清单见下表。交付评审时逐行扫一遍，出现任意一条就回到"来源"列补完再重跑；这不是知识测验，是上线前的实物检查。

| 反模式 | 典型症状 | 根因 | 修正动作 | 来源 |
| --- | --- | --- | --- | --- |
| 可变对象作默认参数 | 函数像"记住了上次的值" | 默认值在定义时求值一次 | 用 `None` 占位，在函数体内新建容器 | 4_1 |
| 类属性放可变容器 | 一个实例追加，所有实例都看得见 | 类属性被全体实例共享 | 移到初始化里逐实例新建，或用 `default_factory` | 5_1 |
| 用共享默认值批量建容器 | 每个分组都躺着全部数据 | `fromkeys` 第二参数、`[[ ]] * n` 只求值一次 | 改用推导式，让每次迭代新建对象 | 3_4 |
| 切片当深拷贝 | 改了副本，嵌套层的数据跟着变 | 只复制外层引用，不复制元素对象 | 嵌套结构用 `deepcopy` 或逐层新建，并注明共享到第几层 | 3_1 |
| 装饰器不保留函数身份 | 调试与文档里函数名全变成包装器 | 少了 `functools.wraps` | 包装层加 `wraps`，再断言 `__name__` 与文档串 | 4_1 |
| 用脚本路径直接启动包内模块 | 本地能跑，CI 报导入错误 | 包上下文不成立，相对导入失效 | 改用 `python -m 包名.模块`，按已安装形态验证 | 6_1 |
| 模块顶层写副作用 | 导入一次就连接、读配置或起线程 | 导入是带缓存的执行 | 顶层只放定义，副作用收进 `main` 守卫或显式初始化函数 | 6_1 |
| 只留宽松依赖不留锁定版本 | 同一份代码隔天装出不同结果 | 声明给人看，缺机器复现依据 | 同时提交锁文件，干净环境按锁文件重建 | 6_5 |
| 天真时间与带时区时间混用 | 跨时区对账总差几笔 | 两边语义不一致，还手算固定偏移 | 入口统一为带时区时刻，换算走 `zoneinfo` | 7_1 |
| 外部调用不设超时 | 批处理偶发卡住，重启就好 | 命令或请求没有超时与返回码检查 | 参数用列表、显式设超时、检查返回码并分别记录输出 | 7_1 |
| 重试无退避无幂等 | 下游抖动升级成风暴，写操作重复 | 立即重试且没有去重键 | 指数退避加抖动、总耗时上限、入口生成幂等键 | 11_1 |
| 起任务不写退出条件 | 在途任务数只涨不降 | 没有取消信号与收敛点 | 每类任务在退出条件表里写"谁让它停"，并等待收敛 | 8_3 |
| 只统计完成数量不取结果 | 批量任务报"全完成"，却丢了错误 | 异常封存在 `Future` 里，不取就不抛 | 逐个调用 `result()`，失败项连同原始输入进死信列表 | 8_1 |
